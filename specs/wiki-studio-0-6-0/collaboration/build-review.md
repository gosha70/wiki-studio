# Peer Review: wiki-studio-0-6-0 — Build Phase

**Reviewer**: deepseek
**Scope**: both
**Rounds**: 2
**Verdict**: PASS

## Summary

The Round 1 fixes are largely sound: the receipt-ignore rule in `_remove_source_dir`, the `_classify_committing` hardening, the `_find_complete_archive` name filter, the `O_NOFOLLOW` lock open, the partial-write loop in `_write_diagnostics`, the `rmdir`-only proposals-dir cleanup, the dry-run leftover guard, and the hex-digest validation all address the reported issues. I found one new correctness gap introduced by the `_remove_source_dir` change (a source file deleted after capture is now silently accepted, which the builder documented but which contradicts the "only while it still matches the archive" contract in a way that can lose a curator's intent), plus a few smaller issues around the receipt-ignore set and the `_finish_committed` archive-files path.

## Findings

- [warning] f-6cf78355: The fix for f-20e6d8ec added `RECEIPT_FILE_NAME` to the ignore set, which is correct, but the same change means a source file that was *deleted* after capture is now silently accepted (the builder documented this as intended). The docstring in `_remove_source_dir` says "only while every file in it matches the archive", but a deleted file is not a match — it is an absence. The archive is complete, so the outcome is safe, but the user's deletion is silently discarded and the directory is removed. This is a deliberate trade-off, but the docstring's "every file in it matches" wording is now inaccurate; it should say "every file present in it matches, and no new file appeared". (src/wiki_studio/promoter.py)
- [warning] f-111a111c: When `archive is None`, `archive_files` is built from `capture.files[rel] for rel in manifest` plus `receipt_path.read_bytes()`. The `manifest` is the receipt's `submission_manifest`, which is the *captured* manifest. But `capture` here is a fresh `_capture_submission(proposals_dir, skip=...)` of the *current* directory. If the directory has a file that is in `manifest` but was modified after capture, the `changed` check catches it and raises `payload_changed` — good. But if the directory has a file that is *not* in `manifest` (added after capture), it is silently dropped from `archive_files` (the loop is `for rel in manifest`), and `_remove_source_dir` will then report it as "new" and raise `payload_changed`. That is the intended behaviour, but the error message from `_remove_source_dir` will name the new file, while the `_finish_committed` path already computed `missing`/`changed` and did not include it. The two error paths can disagree about which files are the problem. Minor, but the message could be confusing. (src/wiki_studio/promoter.py)
- [warning] f-e6e583db: `_archive_is_complete` checks `set(files) - {RECEIPT_FILE_NAME} != set(manifest)`. If the archive contains a `.receipt.json.tmp` leftover (shouldn't happen, but a crash during `_write_receipt` in the archive could leave one), it would be counted as an extra file and the archive would be considered incomplete, causing a second archive to be written. The `_remove_leftover_tmp` only removes `.applied/.<name>.<pid>.tmp` siblings, not a `.receipt.json.tmp` inside a published archive. Narrow, but the receipt-tmp name is already known to the module. (src/wiki_studio/promoter.py)
- [warning] f-986a9b7a: `_classify_committing` returns True when every tracked write is at its post-commit state. `_resolve_receipt` then rewrites the receipt as `committed` and calls `_finish_committed`. But `_finish_committed` re-reads the directory and compares against `manifest`. If the directory was modified between the `_classify_committing` read and the `_finish_committed` capture (a concurrent writer — but the lock is held, so no cooperating writer; a direct edit is possible), the `changed` check catches it. That is correct. However, `_classify_committing` reads `live.read_bytes()` for each tracked path, and `_finish_committed` re-reads the whole directory — the two reads are not atomic with respect to each other, but the lock serialises cooperating writers. No issue in practice; noting for completeness. (src/wiki_studio/promoter.py)
- [warning] f-2b570bcc: The `ignore` parameter is a tuple `(RECEIPT_FILE_NAME, _RECEIPT_TMP_NAME)`. `_mismatches` builds `skipped = set(ignore)` and skips those rels. But `_directory_files` returns *all* entries (files and symlinked dirs), and `_mismatches` checks `path.is_symlink() or not path.is_file()` before the `rel in skipped` check? No — the `rel in skipped` check is first, so a symlink named `receipt.json` would be skipped. That is correct (the receipt is the promoter's file). But a symlink named `.receipt.json.tmp` would also be skipped, which is fine. No issue. (src/wiki_studio/promoter.py)
- [warning] f-8f05a853: `_capture_submission(proposals_dir, skip=frozenset({RECEIPT_FILE_NAME, _RECEIPT_TMP_NAME}))` in `_finish_committed` skips the receipt and its tmp. But `_capture_submission` also refuses symlinks and non-regular files. If the directory contains a symlink named `receipt.json` (planted by a curator), the `skip` check happens *before* the symlink check (`if rel in skip: continue`), so the symlink is silently skipped rather than refused. That is arguably correct (the receipt is the promoter's file and is about to be replaced), but it means a symlink at `receipt.json` is not refused in the `_finish_committed` path, while `_load_receipt` refuses it in the `_promote_locked` path. Inconsistent, but the `_load_receipt` check runs first in `_promote_locked`, so the symlink is refused before `_finish_committed` is reached. No issue in the current flow. (src/wiki_studio/promoter.py)
- [warning] f-9f770795: `_archive_submission` calls `_find_complete_archive(applied_root, name, digest, manifest)` where `manifest` excludes `RECEIPT_FILE_NAME`. `_find_complete_archive` then calls `_archive_is_complete(candidate, manifest)`, which checks `set(files) - {RECEIPT_FILE_NAME} != set(manifest)`. If the candidate archive has a `curator-delta.md` that is not in the manifest (it is staged by `_stage_audit_archive` into the *wiki* archive, not the `.applied/` archive — wait, the `.applied/` archive is the captured submission plus the receipt, so `curator-delta.md` is not in it). The `.applied/` archive contains exactly the captured files plus `receipt.json`. So `set(files) - {RECEIPT_FILE_NAME}` should equal `set(manifest)`. Correct. (src/wiki_studio/promoter.py)
- [warning] f-e1c464aa: `_archive_and_cleanup` catches `OSError` and returns None, but `_remove_source_dir` raises `PromoteApplyError` (a subclass of `IngestError`, not `OSError`) for `payload_changed`. That propagates out of `_archive_and_cleanup`, out of `_commit_and_archive`, and out of `promote`. The wiki is already committed, the archive is complete, and the directory is left in place. The caller sees exit 10 with `payload_changed`. That is the documented behaviour. Correct. (src/wiki_studio/promoter.py)
- [warning] f-24bf24d5: `_finish_committed` calls `_archive_and_cleanup(proposals_dir, paths, archive_files, receipt)`. If `_archive_submission` raises `OSError`, `_archive_and_cleanup` returns None, and `_finish_committed` returns a `PromoteResult` with `archived_dir=None`. The caller (CLI) prints "not archived (the archive step failed after the commit...)". That is correct. But if `_remove_source_dir` raises `payload_changed`, it propagates. The `_finish_committed` path already checked `capture.digest != digest or missing or changed` before building `archive_files`, so a `payload_changed` from `_remove_source_dir` would mean the directory changed *between* the `_capture_submission` and the `_remove_source_dir` — a narrow race, but the lock is held, so only a direct edit could cause it. Correct behaviour (refuse, leave in place). (src/wiki_studio/promoter.py)
- [note] f-94f83a28: The fix changed the check to `proposals_dir.parent.name == APPLIED_DIR_NAME`. This is correct for a proposal directly under `.applied/`. But a proposal under `.applied/<name>/subdir/` would not be treated as applied (its parent is `<name>`, not `.applied`). That is arguably correct (a subdirectory of an archive is not the archive itself), but a caller passing a subdirectory of an archive would get a fresh promote attempt, which would fail on `plan.json not found` or `create target already exists`. Acceptable. (src/wiki_studio/promoter.py)
- [note] f-4aed4455: `_is_hex_digest` checks `len(value) == 64 and all(c in "0123456789abcdef" for c in value)`. This is correct for lowercase hex. But `_sha256` produces lowercase hex, so the check is consistent. A receipt with uppercase hex would be refused as corrupt. That is correct (the promoter never produces uppercase). (src/wiki_studio/promoter.py)
- [note] f-14ba611f: The fix added `not isinstance(dev, bool) and not isinstance(ino, bool)`. Correct. But the `usable` check also requires `dev != 0 and ino != 0`. A filesystem that legitimately reports `st_dev == 0` (some network filesystems) would be refused as `wiki_identity_unavailable`. That is the documented behaviour ("zero values count as unavailable"). Correct. (src/wiki_studio/promoter.py)
- [note] f-2211f4d8: The fix loops on `os.write` over a memoryview. Correct. But `os.ftruncate(fd, offset + len(text))` truncates to the diagnostics length. If a previous holder wrote longer diagnostics (e.g. a longer hostname), this truncates them. The lock is held, so no concurrent writer. Correct. But the `offset` for msvcrt is 1, and the truncate is `offset + len(text)`, which is correct (the locked byte at offset 0 is preserved). (src/wiki_studio/wikilock.py)
- [note] f-11711f54: The fix uses `getattr(os, "O_NOFOLLOW", 0)`. On platforms without `O_NOFOLLOW`, the flag is 0 and a symlink at the lock path would be followed. The test is skipped where `O_NOFOLLOW` is absent. That is the documented behaviour ("where the platform has it"). Correct. (src/wiki_studio/wikilock.py)
- [note] f-89530b02: The fix replaces `read_bytes()` with `_ends_with_newline`, which seeks to the last byte. Correct. But `_ends_with_newline` opens the file with `path.open("rb")` and seeks — if the file is empty, `size == 0` returns True. Correct. If the file is a symlink, `path.open` follows it. The lock is held, so no concurrent writer. Correct. (src/wiki_studio/audit.py)
- [note] f-d6f238fc: The fix pops `hash_recipe` when it is None. Correct. But `dataclasses.asdict(record)` includes `hash_recipe: None` for a record with `proposal_hash=None` (e.g. a reject). The pop removes it. Correct. For a record with `hash_recipe=2`, the key is kept. Correct. (src/wiki_studio/audit.py)
- [note] f-dd02fc05: `payload_digest_from_files` filters `files` to `plan.json` and `preview/` entries. Correct. `_canonical_digest` sorts by `rel.encode("utf-8")`. Correct (LC_ALL=C byte order). (src/wiki_studio/audit.py)
- [note] f-e133abc1: `_identity_files` refuses symlinks for `plan.json`, `preview/`, and every file under `preview/`. Correct. But it does not refuse a symlink at the proposal directory itself (e.g. `proposal_dir` is a symlink to another directory). `_capture_submission` in the promoter also does not refuse a symlink at the proposal directory. A symlink at the proposal directory would be followed by `os.walk` (which does not follow symlinks by default, but the top-level `proposal_dir` is the walk root, so it is followed). That is arguably correct (the caller chose the directory), but it means a symlinked proposal directory is accepted. The docs say "a symlink anywhere in it is refused" — "in it" means inside, not the directory itself. Correct. (src/wiki_studio/audit.py)
- [note] f-1ba8afdd: The fix creates `<name>-2`, `-3`, ... on collision. Correct. But the loop is `while True` with `candidate.mkdir(parents=True, exist_ok=False)`. If `output_dir` is a symlink to an existing directory, `mkdir(exist_ok=False)` raises `FileExistsError`, and the loop tries `<name>-2`. Correct. If `output_dir` is a symlink to a non-existent path, `mkdir` creates the target (following the symlink). That is a potential issue: a symlink at the proposal path would be followed. But the lock is held, and the caller chose the name. Narrow. (src/wiki_studio/ingestor_multi.py)
- [note] f-905c0de4: The fix uses `rmdir` with `contextlib.suppress(OSError)`. Correct. But `rmdir` only removes an empty directory; if another writer created a file in `proposals_dir` while this call waited for the lock, `rmdir` raises `OSError` (suppressed), and the directory is left. Correct. (src/wiki_studio/api.py)
- [note] f-4e006159: The fix catches `Exception` and calls `_discard_partial_proposal`, then re-raises non-OSError. Correct. But `write_patch_set_dir` can raise `PromoteApplyError` (lock timeout), which is an `IngestError`, not an `OSError`. The `except Exception` catches it, discards the partial proposal (which may not exist), and re-raises. The `_discard_partial_proposal` calls `shutil.rmtree(output_dir, ignore_errors=True)` — safe if the directory doesn't exist. Correct. (src/wiki_studio/api.py)
- [note] f-c7fc0d1c: The fix validates `timeout >= 0` (rejects NaN and negatives). Correct. `inf` passes (`inf >= 0` is True). Correct. The `float(timeout_value)` conversion catches `ValueError`. Correct. (src/wiki_studio/paths.py)
- [note] f-620cdefb: The fix injects `[reason=...]` into the prefix. Correct. But `getattr(exc, "reason", None)` on an `IngestError` that is not a `PromoteApplyError` returns None (the base class has no `reason` attribute). Correct. (src/wiki_studio/cli.py)
- [note] f-412cff45: The builder disputed f-d39e847e, claiming the `else` branch is reachable when `n == deletions`. The test asserts `fail.calls == n` and, in the `else` branch, `self.assertEqual(n, deletions)`. If the branch is reachable, the assertion is correct. If it is not reachable, the branch is dead code but the test still passes. The builder's analysis is plausible (the root `rmdir` is the last call, and if it fails, the directory is empty and the retry takes the empty-leftover path). Accepting the dispute. (tests/test_promote_recovery.py)
