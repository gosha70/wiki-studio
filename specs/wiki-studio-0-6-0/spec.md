# Spec: wiki-studio 0.6.0 — safe changes (Release A)

## Why

Five defects on `main` break promises the README makes. Two promotes that
start together revert each other's pages, because commit writes back every
staged page that differs from the live one. A replacement carries no record
of the page it was drafted from, so a stale draft overwrites a newer page.
A symlinked page is written through to its target, a page may link to a file
outside the project, and `find` follows such a link. The query answer check
accepts a fabricated quotation and an answer with no evidence. "Atomic
promotion" means rollback on exception, not crash safety. This release fixes
the first four, states the fifth honestly, and makes each reproduction a
regression test. It ships before any new contract or promotion campaign.

The claim this release earns is bounded: Wiki Studio writers that cooperate
through its API or CLI on one machine do not lose each other's changes and do
not apply stale replacements. Safety across the memkernel stack additionally
depends on memkernel's outer rollback, which is not changed here.

## User Scenarios

### US1: Two writers, no lost update (Priority: HIGH)

**Given** two proposals that each update a different page, promoted by two processes that start together
**When** both `wiki-studio promote` calls return
**Then** both pages carry their change, each promote wrote only the paths its patch-set named, the second waited on the wiki lock before staging, and each has its own archive and receipt

### US2: A stale replacement is refused (Priority: HIGH)

**Given** an agent that read page A, another writer that then committed page A′, and a proposal that replaces A with content drafted from A
**When** the proposal is promoted
**Then** promote exits 9 naming the page and writes nothing; a proposal whose replacement carries no base revision is refused the same way unless the caller passes the compatibility option, in which case the receipt records the page as unguarded; creates and appends from older proposals promote unchanged

### US3: The wiki stays inside the wiki (Priority: HIGH)

**Given** a wiki with a symlinked page, a page that links to an absolute path, an index entry that points outside the wiki, and a proposal whose preview pointer escapes the proposal directory
**When** lint, promote and `find` run
**Then** lint reports the links, promote refuses the symlink and the escaping pointer before reading or writing anything, and `find` never lists a file outside the wiki; `../` source references inside the configured root stay legal

### US4: An answer carries real evidence (Priority: HIGH)

**Given** a backend reply whose citation quotes text that is not in the cited page, or that answers with no citation
**When** `query` validates the reply
**Then** it exits 4 naming the page; a fragment is checked against the page content that was in the prompt, not a file reread afterwards; the abstention form (empty answer, one citation to the index) still passes

### US5: The guarantees are stated as they are (Priority: HIGH)

**Given** the README, SECURITY.md and the promoter docstrings
**When** 0.6.0 is released
**Then** no document says "atomic" without qualification, the fact and stale-source checks are described as heuristics, the per-operation upgrade policy is in the CHANGELOG, memkernel's outer rollback is listed as a limitation, and the version is 0.6.0

## Requirements

- **FR-001 (commit scope)**: `_commit_stage_to_wiki` MUST write only the paths named by the patch-set's edits (including `index.md` and `log.md` appends) plus this proposal's own archive under `.audit/proposals/`. Both staged-tree collectors (`*.md` and `.audit/proposals/*/plan.json`) MUST be scoped this way. A staged file outside that set is never written back.
- **FR-002 (the wiki lock)**: A new module `src/wiki_studio/wikilock.py` MUST provide `WikiLock`, an OS advisory lock held on an open file descriptor: `fcntl.flock(fd, LOCK_EX)` on POSIX and `msvcrt.locking` on Windows, behind one interface. Ownership is the OS lock; no PID-file ownership, no stale-lock reclamation, and the lock file is never deleted or recreated while contenders may hold it. PID, hostname and start time MAY be written into the file as diagnostics only. The lock file is `<resolved-wiki-parent>/.<wiki-dir-name>.wiki-studio.lock`, keyed to `wiki_dir.resolve()`, so two spellings of one directory share it; it lies outside the wiki, so staging and lint never see it. Acquisition waits up to a timeout (default 30 s; `--lock-timeout` and `WIKI_STUDIO_LOCK_TIMEOUT`); on expiry `PromoteApplyError` with `reason="lock_timeout"`, exit 10. The lock is held from before staging to after the archive move, and taken by every cooperating entry point: `promote`, `propose --promote`, the ingest-log append in `audit.py`, `audit-flush` while it reads and commits the log, and `api.promote`. CI MUST run the lock tests on one Windows job; if that job is not added in this release, the "OS Independent" classifier MUST be narrowed to POSIX in the same release.
- **FR-003 (receipts and submission identity)**: The archived `plan.json`, `preview/` and `.ingest-snapshot/` MUST be byte-identical copies of the submitted proposal. Execution metadata MUST go in `receipt.json` in the proposal directory (moved with it into the archive): `state` (FR-004), `submission_digest`, `plan_sha256`, planned paths with the sha256 each live page is expected to hold after commit, written paths, `unguarded_paths`, lock wait, timestamps, and `promoter` as software identity only (package name and version, entry point `cli` or `api`). The submission identity is `submission_digest`: the canonical full-payload digest over the exact bytes used during promotion, never the plan digest alone, because `plan.json` holds pointers and a curator can change a preview without changing the plan. The identity covers the applied payload: `plan.json` plus every file under `preview/`, hidden files included, with no component exclusion. The `.ingest-snapshot/` directory is provenance: captured and archived with the proposal, and outside the identity by rule. `audit.proposal_hash` today excludes dot-prefixed components and files outside `preview/` while the loader accepts a pointer to either (`preview/.line.md`, `line.md`), so its content can change without changing the hash; promote MUST reject a `preview` pointer that does not resolve to a regular file under `preview/` (exit 4 naming the pointer), and the digest MUST be computed by one canonical function that enumerates `preview/` without exclusions, used by both the ingest log and the receipt. That function is a new recipe, `payload_digest` (recipe 2), beside the published recipe 1 (`proposal_hash`, the "exact recipe" in `audit-rules.md`, dot exclusion included), which every ingest-log record since 0.1.0 used and which MUST stay implemented for verifying those records. The receipt records `digest_recipe: 2`; a new ingest-log record carries the optional key `hash_recipe: 2` with `v` unchanged at 1, and a record without the key was produced by recipe 1. The audit lint's record check today rejects any key outside the required set, so it MUST accept that optional key, and only that key, in `v: 1`. `audit-rules.md` MUST document recipe 2 beside recipe 1 and state which records use which; the CHANGELOG lists the change under Changed, because a consumer that recomputes a value against the documented recipe is affected while the audit lint's format check is not. The two values identify different things: the ingest log records the hash of the generated payload when the proposal is written, and the receipt records the digest of the promoted payload. They are equal when a proposal is promoted unchanged; when a curator edits a preview before promotion, the ingest-log entry MUST stay as written, the receipt and the archive MUST identify the edited payload, and `curator-delta.md` records the difference. No check may require the two to be equal. The enumeration MUST pass every file it reads through the FR-012 proposal boundary, including files no pointer references. Promote MUST capture the payload once: under the lock, after the FR-012 proposal-boundary checks, it reads `plan.json`, every file under `preview/` and every file under `.ingest-snapshot/` into memory in one pass, and parsing, the digest, staging, the receipt's tracked writes and the archive copy all use that capture; the directory is never reread during the promotion. Proposal writers MUST NOT write into an existing proposal directory: `api.ingest` today reuses `<date>-<source-stem>` with `exist_ok=True`, so a second ingest of the same source on the same day overwrites a proposal that may be mid-promotion; the numbered-suffix creation (`<name>`, then `<name>-2`, `-3`, with `exist_ok=False`) MUST live in `write_patch_set_dir` (`ingestor_multi.py`, today `output_dir.mkdir(parents=True, exist_ok=True)`), which every writer goes through, taken under the wiki lock, with `ingest` feeding it the date-and-stem name and `api.propose` its chosen name; the directory actually created is returned to the caller. The archive MUST be written from the capture, not moved from the directory: step 4 writes the captured `plan.json`, previews and snapshot plus the receipt into `.applied/<name>/` (`-2`, `-3` on a clash) and fsyncs it, and only then removes the original directory, and only if that directory's digest still equals the capture. A mismatch leaves the directory in place and exits 10 with `reason="payload_changed"`, naming the leftover directory and the completed archive; the archive is complete and correct at that point, so the remedy is one line in the message and the docs: delete the leftover directory, or promote it afresh if it is a new proposal. On a retry, a `committed` receipt is resolved as FR-004 states. An interleaving test MUST run an ingest of the same source while a promote of the earlier proposal is held between capture and archive: the ingest lands in a new directory, the receipt and the archive identify the captured bytes, the applied pages equal the captured previews, and the new proposal remains unpromoted. `plan_sha256` is kept separately for provenance. Tests MUST pin that changing the bytes of a hidden preview file, of a file outside `preview/`, or of an unreferenced preview file changes the digest or is refused; that the receipt's digest equals the ingest-log hash for a proposal promoted unchanged; and that for a curated proposal the ingest-log entry is unchanged while the receipt and the archive match the edited bytes and the curator delta. Archive directory names are unchanged from 0.4.0 (`.applied/<name>/`, then `<name>-2`, `-3` on a name clash), so existing consumers keep resolving; two same-named submissions never share a directory, and never share an identity unless their payload bytes are equal. Failed validation attempts and dry runs persist no receipt.
- **FR-004 (commit, receipt and recovery ordering)**: Under the lock, after validation and the FR-008 checks pass, promote MUST proceed in this order: (1) write `receipt.json` into the proposal directory with `state: "committing"`, the submission digest, `wiki_target` (the identity of the wiki being written: `st_dev` and `st_ino` from `os.fstat` on a descriptor opened on the wiki directory under the lock; on POSIX the US3 staging walk opens entries relative to that descriptor (`dir_fd`), so identity and staged reads refer to one directory object, and on Windows, where `dir_fd` is unsupported, identity comes from the directory handle and staging reads by path, documented as the weaker binding; the resolved path is recorded beside them as a diagnostic that is never used to accept; a zero device or inode, as some Windows and network filesystems report, counts as unavailable) and, for every path the commit will actually write (no-op paths whose live content already equals the proposed content are excluded, and this proposal's own audit artifact under `.audit/proposals/` is included), both the sha256 of its pre-commit content (or absence) and the sha256 it will hold after commit, and fsync it; if this write fails, nothing is committed and promote exits 6; (2) commit the files; (3) rewrite the receipt with `state: "committed"` and fsync; (4) archive from the capture as FR-003 states (write `.applied/<name>/` from the captured bytes, then remove the original directory only if its digest still matches). On a later promote of the same proposal directory: a receipt with `state: "committed"` means finish step 4 only, with no appends: when the directory's digest equals the receipt's, the archive is written from the directory's bytes and the directory removed; when it does not, no archive can be written, because the promoted bytes now exist only in the wiki (the wiki-side `.audit/proposals/<name>/` copy holds the plan and the proposal rendering, not the previews, and cannot rebuild it), so promote exits 10 with `reason="payload_changed"`, leaves the directory in place, and its message states that no archive could be written, that the applied pages are identified by the receipt's tracked post-commit hashes, and the remedy: move the directory aside and keep its receipt as the record of what was applied, or promote it afresh if it is a new proposal; a proposal already under `.applied/` returns the recorded outcome with no writes; a receipt with `state: "committing"` is resolved under the lock by comparing each tracked write's live sha256 (or absence) with the receipt: all tracked writes equal to their recorded pre-state means not committed (the receipt is removed and the proposal may be promoted afresh); all equal to their expected post-state means committed (complete steps 3 and 4); any other combination, including a tracked path that matches neither state, exits 10 with `reason="uncertain_outcome"` and a message naming the paths, with no writes. Excluding no-op paths keeps a page that already held its proposed content from reading as a partial commit; including the proposal's own audit artifact keeps a later cooperative writer's changes to shared pages from making a committed proposal look uncommitted. Before any recovery step, archival or outcome report, promote MUST compare the receipt's `wiki_target` with the wiki it was invoked against by device and inode only; a mismatch exits 10 with `reason="wiki_mismatch"` naming both targets, with no writes, so a `committing` receipt from wiki A is never classified using wiki B's files, a `committed` receipt never reports success into B, and a different directory created at A's old path is refused even though its path matches. Where the platform or filesystem reports no usable identity (`st_ino` or `st_dev` of 0), promote MUST NOT fall back to the path: it exits 10 with `reason="wiki_identity_unavailable"` naming the receipt. The docs state that recovery of an interrupted promotion needs a filesystem with stable inode identity, and give the manual remedy for a `wiki_mismatch` or unavailable identity on a wiki that was legitimately restored or re-cloned at the same path: compare the receipt's tracked writes (pre- and post-commit sha256) with the live pages, then either finish by promoting afresh or discard the proposal directory by hand; promote never does this automatically. Before treating a retry as already committed, promote MUST recompute the submission digest from the directory's bytes and require it to equal the receipt's; a missing or corrupt receipt is never treated as committed and never causes silent reapplication. This protocol covers failures between these steps and does not claim recovery from arbitrary process crashes during step 2 beyond the existing exception rollback; the docs say so. Tests inject faults after step 1, during step 1, during step 3 and during step 4, and cover an update whose proposed content is already identical to the live page (a no-op: excluded from tracking, recovery after step 1 reads as not committed), a retry of an interrupted promotion against a different wiki through `--wiki-dir` and through `WIKI_STUDIO_WIKI_DIR`, each refused with `wiki_mismatch` and nothing written to either wiki; and wiki A renamed with wiki B created at A's old path, retried with a `committing` and with a `committed` receipt, each refused with `wiki_mismatch`.
- **FR-005 (base revision in the edit model)**: `PageEdit` MUST gain `base_sha256: str | None = None`, added last with a default so positional construction keeps working; `plan.json` MUST gain the optional key `edits[].base_sha256`, documented in `docs/patch-set-format.md` under the format's minor-version rule. The hash is sha256 over the page bytes as read.
- **FR-006 (one read gives content and hash)**: `api.read_page(path, paths)` MUST read the page once and return the bytes, the UTF-8 decoded text and the sha256 of those exact bytes; a page that is not valid UTF-8 is a `ContractViolationError` (exit 4) and returns no content. `wiki-studio read <path>` prints the text; `--json` prints `{"path", "sha256", "content"}` with the decoded text, never raw bytes. The path is wiki-relative and MUST pass FR-012's wiki boundary before the read. `find` lists pages and does not hash them; `info` stays configuration and capabilities. The documented agent procedure is: read with `read`, draft from that content, record its hash.
- **FR-007 (the hash is what the author read)**: For `ingest`, `wiki_state.load_wiki_state` MUST read each selected page once, returning bytes, decoded text and sha256 from that one read; the text placed in the prompt and the hash attached to the edit MUST come from the same bytes (today the selection code reads candidate pages more than once; that is replaced). The model never supplies or reconstructs a hash. For `propose --from`, the draft directory MAY carry `<draft>/.base.json` mapping wiki path to sha256; `propose` MUST NOT fill a missing hash from the live page, and an `update` without a manifest entry is unguarded. For `api.propose`, the caller supplies it. No code path upgrades an older proposal by attaching a current hash.
- **FR-008 (preconditions under the lock)**: After staging and while holding the lock, immediately before commit, promote MUST check: `create` requires absence of the live target; `append-index` and `append-log` apply to the current live content; `update` with `base_sha256` requires the live page's sha256 to equal it. A mismatch is `PromoteValidationError` (exit 9) naming the page, with nothing written.
- **FR-009 (unguarded updates)**: An `update` without `base_sha256` MUST be refused with exit 9 and a message naming the page and the two remedies (regenerate from a fresh `read`, or pass the compatibility option). With `--allow-unguarded-updates` (CLI) or `allow_unguarded_updates=True` (`api.promote`) it is applied and listed under `unguarded_paths` in the receipt and in `PromoteResult`. Help text and docs MUST call this "compatibility mode with incomplete conflict protection" and MUST NOT describe it as preventing stale overwrites.
- **FR-010 (structured findings)**: `PromoteResult` MUST gain `unguarded_paths: list[str]` and `warnings: list[str]`, added last with defaults.
- **FR-011 (dry run on a snapshot)**: `promote --dry-run` MUST acquire the lock, stage, check FR-008's preconditions against live while holding the lock, release the lock, then validate the staged copy. It writes no wiki content, no receipt and no proposal change; the lock file itself may be created. Its help text says the result is point-in-time evidence and a real promote checks again.
- **FR-012 (containment boundaries)**: One canonical check, `paths.contain(candidate, boundary)`, resolves both sides and refuses a candidate outside the boundary or reached through a symlink; it is used on every read and write surface, new and existing. Wiki boundary: page writes, staging reads, `read_page` and `wiki-studio read`, and navigation reads (`find`, `query`, the eval selector). Proposal boundary: `plan.json` itself, every `preview` pointer, every file the digest enumeration under `preview/` reads (an unreferenced preview symlink today makes `audit.proposal_hash` read outside the proposal), every file under `.ingest-snapshot/` read for `curator-delta.md`, and `receipt.json`; each is checked before its content is read, and a directory enumeration MUST refuse a symlink (file or directory) with `PromoteValidationError` naming it. Source boundary: a local source reference in page text resolves inside the configured root or an explicitly allowed source root. Allowed source roots are configured by `--source-root PATH` (repeatable) and `WIKI_STUDIO_SOURCE_ROOTS` (path-separator list), default empty, exposed as `WikiPaths.source_roots`. Checks use `resolve()`, never `normpath` alone. Staging MUST refuse any symlink inside the wiki (file or directory) with `PromoteValidationError` naming it, and commit MUST re-check with `os.lstat` under the lock. Tests cover absolute paths, `../` escapes and symlink targets on every surface named here, including an unreferenced symlink under `preview/` and under `.ingest-snapshot/` that no pointer names.
- **FR-013 (link rule)**: `md_links` (`lint.py:112-122`) today keeps only targets ending in `.md`, so an image or data link such as `![d](../../outside/diagram.png)` is never checked; US3 MUST expand the collector to return every local target (a non-`.md` local target is part of the security boundary) while keeping a separate wiki-page view for reachability. `lint_wiki` MUST then classify each target: `http`, `https` and `mailto` targets are not filesystem links; a local `.md` target that resolves inside the wiki directory is a wiki-page link and must exist; a local `.md` target outside the wiki, and any local non-`.md` target (images, data files, source files), is a source reference and must resolve inside the root or an allowed source root; the reachability check counts only wiki-page links. Absolute targets and targets that leave the root are violations. `../` targets that stay inside the root remain legal. An index entry whose target resolves outside the wiki directory is a violation, so promote rejects it; `_extract_index_links` MUST apply the same rule as a defence, shared by `find`, `query` and the eval selector. Both evaluation runs MUST remain byte-identical.
- **FR-014 (citation evidence)**: `DefaultQuerier.query` MUST validate each citation's fragment against the captured `index_md` and `pages_content` supplied to the backend, never against files reread after the backend returns; the fragment must occur in that text after whitespace normalisation, else `ContractViolationError` (exit 4) naming the page. A non-empty answer MUST carry at least one citation. The abstention form (empty answer, one citation to `index.md` whose fragment occurs in the captured index) remains valid. Docs state that the check verifies quotation against the prompt snapshot, not logical support.
- **FR-015 (honest guarantees)**: README (the promote section and line 79), SECURITY.md (line 32) and the promoter docstrings MUST describe promotion as "validated, serialised against other wiki-studio writers on the same machine, rolled back on failure; not crash-safe across files, and uncoordinated readers may observe intermediate state." The fact check MUST be described as a heuristic for citations, identifiers and quantities that does not detect changes of meaning; the stale-source check as verifying that cited paths exist, not the recorded revision. The lock's scope (one machine, one filesystem; not distributed; not protection against direct edits; network filesystems out of scope) MUST be documented.
- **FR-016 (release)**: Version 0.6.0 in `pyproject.toml`, `src/wiki_studio/__init__.py` and the CLI contract test; README banner pinned to `v0.6.0`; CHANGELOG `[0.6.0]` with Added (lock, receipts, `read`, preconditions, containment boundaries, citation evidence), Changed (commit scope, link rule, receipt files in archived proposals, digest recipe 2 for receipts and new ingest-log records with recipe 1 kept for older records), Security (symlink and outside-link escapes, credited to the reporter), Upgrade notes stated per operation (creates and appends from older proposals promote unchanged; replacements without a base hash are refused until regenerated from a fresh `read`, or applied under the compatibility option, recorded as incomplete conflict protection), and Limitations (memkernel's outer whole-wiki snapshot and rollback can still undo another writer's committed changes until memkernel holds the same lock across its lifecycle or removes that workaround; mixed-writer safety across the stack is claimed only when both halves ship). The CHANGELOG MUST NOT state what memkernel's next release does. The agent arm stays pinned at 0.4.1 with its note. The enforced coverage threshold MUST match the stated gate: `--cov-fail-under=92` in `.github/workflows/ci.yml`, `CLAUDE.md` and `specs/wiki-studio-0-6-0/automation.json`. `eval/navigation/run2_protocol.py` (which reads `.applied/<proposal_dir>/plan.json`) MUST keep working unchanged, and a test MUST pin that the archive layout it depends on is unchanged.
- **FR-017 (fallback)**: If 0.6.0 slips, the contract-compatible subset MAY ship first as 0.5.1: FR-001, FR-002, FR-012, FR-013, FR-014 and FR-015. Receipts, `read`, `base_sha256`, the compatibility option and `PromoteResult` fields wait for 0.6.0, because each adds to a published format or API.

## Constraints

- **Standard library only.** `fcntl`, `msvcrt`, `hashlib`, `os` and `pathlib` suffice; no new runtime or dev dependency.
- **Contracts.** Exit codes 0 and 2..11 unchanged (9 for revision conflicts, 10 with `reason="lock_timeout"` for the lock, `"uncertain_outcome"`, `"wiki_mismatch"`, `"wiki_identity_unavailable"` and `"payload_changed"` for recovery); the patch-set format gains optional keys only; `api` changes are additive with defaults; `promoter.py` stays the single writer into the wiki (the single-writer test stays green).
- **Submitted bytes are never rewritten.** No code path edits an archived `plan.json` or preview; execution metadata lives in `receipt.json`.
- **No production pause hook.** Tests force interleavings from a test bootstrap that patches the child process before it calls `cli.main`; no environment variable in shipped code can pause promotion.
- **Cross-product gate.** Mixed-writer safety across the memkernel stack is not claimed by this release. A combined integration gate (memkernel bridge compatibility: creates and appends through `api.propose`, receipt and `.applied/` layout, lock coordination) is tracked as the first item of Release B and must pass before any combined safety claim.
- **Out of scope.** Asserted actor attribution, schema version and root manifest, supersession keys, FTS5, MCP, curation-debt reporting, quickstarts, crash-safe multi-file transactions, distributed or network-filesystem coordination, changes to memkernel.
- **Gate.** `poetry run ruff check src/ tests/ eval/ && poetry run ruff format --check src/ tests/ eval/ && poetry run mypy src/ && poetry run pytest -q -p no:cacheprovider --cov=wiki_studio --cov-fail-under=92` stays green; coverage does not fall below the current level (92%); both evaluation runs' determinism tests stay green.
