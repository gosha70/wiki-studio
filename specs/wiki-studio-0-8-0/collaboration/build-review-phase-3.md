# Peer Review: wiki-studio-0-8-0 — Build Phase

**Reviewer**: deepseek
**Scope**: both
**Rounds**: 2
**Verdict**: PASS

## Summary

The Round 1 fixes are largely in place: the held-out guard now reads the live config once, `_committed_bytes` resolves the commit before reading, `random_hit_at_5` is clamped, the post-hoc path checks the original run's config hash, the gold validation rejects `..` escapes, and the probe watches the whole held-out directory. A few correctness gaps remain, mostly around the `tune` tie-break when the untuned config is absent from the candidate list, the `_inside` symlink asymmetry, and the in-memory latency comparison still not matching the cached workload.

## Findings

- [warning] f-123218e2: The Round 1 finding f-820fc3f7 was marked "fixed", but the code still computes `tie = -1` only when the untuned config is in the candidate list. The guard `if untuned not in candidates: raise` was added, so the "silently does nothing" case is now refused — good. However, the `selection_rule` string still claims "then the untuned configuration, then grid order", and the `tie` value for the untuned config is `-1` while every other candidate gets its `position` (0..N-1). If the untuned config happens to be at position 0, its tie value is `-1` and it wins ties against itself — harmless — but if a *different* candidate is at position 0 and the untuned config is at position 5, the untuned config's `-1` still wins, which is the intent. The remaining issue is that `position` is the enumeration index of the *candidate list*, not the grid order, so the "then grid order" clause is only true when `configurations is None`. The rule string is misleading for a custom candidate list. (eval/navigation/discovery.py)
- [warning] f-fde36740: Round 1 f-b9658889 was marked "disputed", but the asymmetry is real: `_inside` resolves both sides, so a symlink *inside* the fixture pointing *out* is caught (good), but a fixture path that is itself a symlink to a directory containing the cache is not caught if the cache is created before the symlink resolves — and more importantly, `WikiPaths.for_root` later uses the *unresolved* `fixture_dir` to build the cache path, so the check and the use disagree on which path is authoritative. The dispute may be that `resolve()` on a non-existent path is fine on modern Python, which is true, but the check is still asymmetric with how the path is later used. (eval/navigation/discovery.py)
- [warning] f-7bd6daeb: Round 1 f-8f846d6e was marked "fixed", but the fix is a docstring disclaimer, not a change to the measurement. The `in_memory_no_cache` timing still measures a different workload than `cold_cache`/`warm_cache` (which stop at `DEFAULT_MAX_CONTEXT_BYTES` and load pages). The README now says "it is a lower bound beside the cached `find` timings, not the same workload", which is honest, but the field name `in_memory_no_cache` still invites a direct comparison. A reader who sees `cold_cache: 3.8ms` and `in_memory_no_cache: 2.3ms` will conclude the cache is slower, which is not what the numbers measure. (eval/navigation/discovery.py)
- [warning] f-385a0281: Round 1 f-dc4de948 was marked "fixed", but the fix is a `raise RunnerError` when `fixture_dir/RESULTS_NAME` is missing — which is correct for the development set. However, the docstring still says "inherited from the fixture's own results for the development wiki (FR-020)", and the fallback path now refuses rather than silently falling back. The remaining issue is that `_ingest_coverage` is called from `compute` for *every* fixture, including a synthetic held-out fixture in tests, and the `is_heldout` check reads `manifest.json` — if a caller passes a fixture with a `manifest.json` that has `set: heldout` but no `ingest.summary`, the function returns `None` for `documents_ingested`/`documents_promoted` and a `rate` computed from the caller-supplied counts. That is the "measured" path, but the summary is empty. (eval/navigation/discovery.py)
- [warning] f-2fce4c32: Round 1 f-1400ee22 was marked "fixed": `step_questions` now calls `sha = _git("rev-parse", commit)` and passes `sha` to `_committed_bytes`, so the bytes checked are from the resolved SHA. Good. But `_committed_bytes` still does `path.resolve().relative_to(REPO_ROOT)` — if `path` is a symlink or if `REPO_ROOT` is itself a symlink, the `relative_to` can raise `ValueError` rather than `ProtocolError`, which would escape the `except ProtocolError` in `main` and crash with a traceback. (eval/navigation/heldout_protocol.py)
- [warning] f-2da51044: Round 1 f-317e8d1c was marked "fixed": the probe now watches `heldout_dir` itself, which covers `questions.json`, `gold.json`, `manifest.json`, `corpus/`, `wiki/`, `proposals/`, and `doc_internal`. Good. But the probe still does not watch `CLAUDE_CONFIG_DIR` if `_run_env` sets it outside `heldout_dir` — the `env` is recorded in the probe record, but the *contents* of that directory are not hashed before/after. If the backend writes its query log there, the probe's `unchanged` check passes while the isolation is actually violated. The Round 1 finding named this specifically. (eval/navigation/heldout_protocol.py)
- [warning] f-0c7d3f8e: Round 1 f-c4e55c14 was marked "fixed": the check now uses `(wiki_dir / target).resolve().is_relative_to(wiki_dir.resolve())`, which rejects `../questions.json`. Good. But the check is `(wiki_dir / target).resolve().is_relative_to(wiki_dir.resolve()) and (wiki_dir / target).is_file()` — the `is_file()` is on the *unresolved* path, so a symlink inside the wiki pointing outside would pass `is_relative_to` (because `resolve()` follows it) but the `is_file()` would also pass. The `resolve()` on the left side means a symlink to a file outside the wiki resolves outside and is rejected — correct. The remaining issue is that `wiki_dir.resolve()` is computed on every iteration; for a large gold set this is O(n) `resolve()` calls on the same directory. (eval/navigation/heldout_protocol.py)
- [warning] f-c0f86c86: Round 1 f-a74b8387 was marked "fixed", but the fix is a test (`test_the_eligible_pages_are_the_ones_find_considers`) that asserts the two agree on the *development* wiki. The duplication remains: `read_eligible_pages` reimplements the eligibility loop, and the test only covers one fixture. If the live `find` changes its eligibility rule (e.g. adds a new `_NEVER_CANDIDATES` entry), the test will catch it *if* the development wiki exercises the new rule — which it may not. The test is a good guard but not a substitute for sharing the code. (eval/navigation/heldout_protocol.py)
- [warning] f-f0cef7e6: Round 1 f-298efdfa was marked "fixed": the test now checks `self.assertIn("manifest.json", pins, ...)` and `self.assertTrue(any(rel.startswith("wiki/") for rel in pins), ...)`. Good. But the failure message for the empty-pins case is still `self.assertTrue(pins, "heldout/wiki/ exists: pin its files, ...")` — a `self.assertTrue` failure is reported as `AssertionError: False is not true : heldout/wiki/ exists: pin its files, ...`, which is readable but not a clear "you forgot to pin" error. The Round 1 finding asked for a clearer error; the message is now clearer but the mechanism is still an assertion. (tests/test_frozen_runs.py)
- [warning] f-99ec9acd: Round 1 f-64abb0c4 was marked "fixed": the test now asserts `self.assertEqual(visited, list(heldout_protocol.STATES[: len(visited)]))` and `self.assertEqual(manifest["state"], visited[-1])`, which enforces the order. Good. But the test still has `if not (HELDOUT / "wiki").exists(): self.assertIn(manifest["state"], heldout_protocol.STATES[: heldout_protocol.STATES.index(heldout_protocol.STATE_INGESTED)])` — this is a conditional assertion that only runs when `wiki/` is absent. Once the owner runs the ingest, `wiki/` exists and this branch is skipped, so the test no longer enforces that the state is before `ingested` when `wiki/` is absent. That is correct (the state *should* be `ingested` or later once `wiki/` exists), but the test name says "moved through the states in order" and the conditional makes it weaker than it looks. (tests/test_discovery_eval.py)
- [note] f-ebc94257: Round 1 f-10c1ecbc was marked "fixed": `random_hit_at_5` is now `min(len(r["selected"]), eligible) / eligible`, which is clamped to 1.0. Good. But `random_hit_at_1` is still `(1 / eligible if r["selected"] else 0.0)`, which is correct (a random draw of one page hits gold with probability 1/eligible), but the `_mean` over entries means a question with an empty selection contributes 0.0, which is correct. No issue. (eval/navigation/discovery.py)
- [note] f-623e366b: Round 1 f-060778a9 was marked "fixed", but the fix is not visible in the diff: `comparable` still strips only `latency` and `ENVIRONMENT_PARAMETERS`, not `parameters.ranker_config_hash`. The Round 1 finding said the hash is a *derived* value, not a measurement, and should be stripped. The current code keeps it, so a hash algorithm change would fail reproduction even though the numbers are identical. The finding was marked "fixed" but the code does not reflect it. (eval/navigation/discovery.py)
- [note] f-0b0dc8bc: Round 1 f-09e3532d was marked "fixed": `run` now calls `_live_config()` once at the top and passes `live` to `heldout_output`, so the config checked is the config that runs. Good. But `heldout_output` still calls `load_config(tuned)` and `ranker_config_hash(load_config(tuned))` — if `run3/ranker-config.json` is edited between the `heldout_output` check and the `compute` call, the run uses `live` (the config read at the top) but the check used the file's hash at check time. In practice this is a single-process CLI, but the ordering is still fragile. (eval/navigation/discovery.py)

If the hash algorithm changes, the `diff` will show a difference that `discovery.reproduce` also shows, so the README and the test agree. No issue, but the README should mention that the hash is compared. (eval/navigation/run3/README.md)
