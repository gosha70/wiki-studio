## Why

0.7.0 made the curation loop governable. Two things still limit who can use
wiki-studio on its own. Discovery is weak and unbounded: `find` and `query`
pick pages by counting the question's words that also occur in a page's slug,
path and first 400 characters, which on the published fixture puts the gold
page first for 3 of 21 questions and within the top five for 10 of 21; five
questions select nothing beyond the index, a question the corpus cannot
answer loads four pages on average, and the five-page cap bounds the page
count, not the bytes. Only shell-capable agents can use it: the surface is a
CLI and a Python API, so an MCP host (Claude Code, Kiro) wraps the CLI itself
and rebuilds the same boundary each time (no model calls, proposal distinct
from promotion, no approval).

The cost is the roadmap's adoption claim, "time to the first accepted
revision on a clean install", which today needs a shell wrapper and a
selector that misses half the time. This release is all of Release C in one
release (owner decision): a second ranker, FTS5 with bm25 over the same
index-linked candidate set, behind the index-first workflow, with a byte
budget, a rebuildable cache outside the wiki, a frozen held-out measurement
that decides the default; and an optional MCP adapter on the official SDK
with a conformance suite and one recorded host run. Release C closes when
the three exit-evidence items exist on the 0.8.0 tag; if the circuit breaker
shelves part of it, 0.8.0 may still ship and Release C stays open.

## User Scenarios

### US1: Ranked discovery with a context budget (Priority: HIGH)

**Given** a wiki whose `index.md` links pages inside the wiki, a question, a runtime whose `sqlite3` has FTS5 and one whose `sqlite3` does not, a page that is not valid UTF-8, a page carrying `superseded_by`, and a page larger than the byte budget
**When** an agent runs `wiki-studio find` or `query` with `--ranker fts5`, with `--ranker index-first`, with `WIKI_STUDIO_RANKER` set, or with no ranker named, and runs `lint` and `promote`
**Then** `index.md` is always loaded first and at most five pages follow within the byte budget, ranked by bm25 under FTS5 or by today's word overlap under index-first, ties broken by index order; without FTS5 selection falls back to index-first with one stderr notice, `ranker` and `fallback_reason` in the result and exit 0; the superseded page and the non-UTF-8 page are never selected and are counted in `ineligible`; the oversized page is skipped, listed in `omitted`, and the next page is tried; the non-UTF-8 page is one structural-lint violation naming its path, fatal for `lint` and for every `promote` until it is fixed; and the frozen evaluation runs reproduce their committed numbers unchanged

### US2: The rebuildable cache (Priority: HIGH)

**Given** a wiki with the FTS5 cache beside its lock file, a page edited by hand with the same size and a restored mtime, a `git checkout` of an older revision, a rename, a delete, a page unlinked from the index, a truncated or foreign cache file, a symlink at the cache path, a read-only directory, and two processes calling `find` at once
**When** `find` or `query` runs after each change
**Then** every call rereads and hashes the eligible pages, diffs them against the cache's content manifest and ranks over current paths only, so the cached ranking equals a fresh in-memory ranking after any sequence of changes; a corrupt cache is removed and rebuilt; a cache that cannot be used makes that call use an in-memory index with one warning and exit 0; the cache never supplies page text to a prompt; the wiki tree is byte-identical before and after every case; and the cache file is never inside the wiki directory

### US3: Discovery evidence (Priority: HIGH)

**Given** the frozen runs 1 and 2 under `eval/navigation/`, the 21 development questions with a gold page, and a fresh held-out corpus (the eight user-facing README files of mapatlas at a pinned commit)
**When** the owner follows the held-out protocol in its fixed order (sources pinned; questions committed before the ingest; pins and an isolation probe recorded; one ingest with no retries; the wiki frozen by sha256; gold assigned and reviewed; everything frozen; tuning on the development set only; one held-out run after the ranker configuration hash is frozen) and the runner reports both rankers
**Then** the frozen runs are byte-identical and their tests pass; `run3/results-untuned.json` is committed before tuning and `run3/results.json` after; `heldout/results.json` is the one held-out run, with the eligible page count and the random baseline beside every hit rate, unanswerable-query behaviour, ingestion coverage, context size and latency (cached beside in-memory); and FTS5 becomes the default ranker only if it is no worse than index-first at hit at 1 and at hit at 5 on the held-out set and at least 15 held-out questions have a gold page and the frozen held-out wiki has at least ten eligible pages, with the CHANGELOG stating which basis the default rests on

### US4: The MCP adapter as an extra (Priority: MEDIUM)

**Given** `pip install 'wiki-studio[mcp]'`, a host that launches `wiki-studio-mcp` over stdio with `--root`, `--wiki-dir`, `--by` and optionally `--disable-tool promote`, a base install without the extra, and a wiki whose policy sets `auto_approve_on_promote`
**When** an agent lists and calls the tools, passes a proposal name with `../`, calls `promote` on the auto-approving wiki, and a tool raises
**Then** exactly `find`, `read_page`, `propose`, `promote`, `lint`, `info`, `findings` and `review_state` are listed, none takes a root, directory, backend, actor or escape-hatch argument, `--disable-tool` only removes tools, `propose` assigns a `page_id` to every create, `promote` resolves a name under the proposals directory and records `entry_point: "mcp"`, the auto-approved promote succeeds with `approved_paths` and a warning naming the policy and the server's fixed actor, every error is `{error, exit_code, message}` from the existing class-to-code table, stdout carries protocol frames only, the base install imports nothing outside the standard library, and the script without the extra prints the install instruction and exits 2

### US5: Conformance suite, a host run, and release 0.8.0 (Priority: MEDIUM)

**Given** the suite under `conformance/mcp/` driving any `--server-cmd` through the SDK's client against a fixture wiki, CI jobs at the SDK floor and at the newest `<3`, and Claude Code at a pinned version running headless against the adapter with `--trace`
**When** CI runs and the owner performs the host run
**Then** the twelve conformance cases pass for each tested protocol version, the `check-host-run` step applies cases 2-9 to the trace and the fixture's end state, the run is recorded under `conformance/runs/<date>-claude-code-<version>/`, `docs/compatibility.md` gains an MCP table, and 0.8.0 ships with its CHANGELOG (the UTF-8 upgrade note, the basis of the default ranker), the README Evidence section, ADR-0003, exit codes 0 and 2..11 unchanged, and any cut named

## Requirements

### US1 — ranked discovery with a context budget

- **FR-001 (modules and the two rankers)**: Two new modules. `src/wiki_studio/discovery.py` holds the FTS5 probe, eligibility, ranking, the budget and selection; `src/wiki_studio/search_index.py` holds the FTS5 table (in memory in US1, on disk in US2) and is the only module that writes the cache file. Constants, defined once in `discovery.py` and imported everywhere: `RANKER_FTS5 = "fts5"`, `RANKER_INDEX_FIRST = "index-first"`, `RANKERS = (RANKER_FTS5, RANKER_INDEX_FIRST)`, `DEFAULT_RANKER` (set to `RANKER_INDEX_FIRST` until FR-029 decides otherwise, so nothing user-visible changes before the evidence exists; owner decision, 2026-10-27, on the PR #52 review), `ENV_RANKER = "WIKI_STUDIO_RANKER"`, `DEFAULT_MAX_CONTEXT_BYTES = 65536`, and the ranker-source strings `flag`, `env`, `default`. `resolve_ranker(flag: str | None = None, *, env=None) -> tuple[str, str]` MUST return `(ranker, source)`: a non-empty flag is `flag`, else a non-empty `WIKI_STUDIO_RANKER` is `env`, else `(DEFAULT_RANKER, "default")`; a value outside `RANKERS` from either source raises `ValueError` naming the value and the two accepted names. `_select_query_candidates` (`querier.py:104-156`) MUST keep its name, signature, body and return value: it is the `index-first` ranker and the named fallback, and `eval/navigation/run.py` keeps importing and calling it directly, so `tests/test_navigation_eval.py` stays green with every frozen number unchanged. `wiki_state._STOPWORDS` MUST NOT change (`test_stop_list_is_the_queriers`); if FTS5 tuning wants a different stop list it is a separate constant in `discovery.py`.
- **FR-002 (FTS5 probe)**: `discovery.fts5_available() -> Fts5Probe` (`available: bool`, `sqlite_version: str`, `reason: str | None`) MUST run once per process (cached) by creating an `fts5` virtual table with the configured tokenizer in a `:memory:` connection; on `sqlite3.OperationalError` it returns `available=False` with the error text as `reason` and `sqlite3.sqlite_version`. The fallback is tested by patching the probe, never by building a Python without FTS5. When the probe is false and the resolved ranker is `fts5`, selection MUST fall back to `index-first`, the result MUST carry `ranker: "index-first"` and `fallback_reason` (the probe's reason), the CLI MUST print one notice to stderr, and the exit code stays 0 (D4). No new exit code and no error for a missing FTS5; a host that requires ranked discovery checks `info.discovery.fts5` (FR-010).
- **FR-003 (non-UTF-8 pages: the helper fix and the structural rule)**: `wiki_state._read_text_or_empty` (`wiki_state.py:147-152`) MUST catch `UnicodeDecodeError` as it catches `OSError` and return the empty string, so every caller is safe without an edit: `querier._select_query_candidates` (the page reads as empty and is never selected), `health_lint` (five call sites; the page is never checked), `prose_lint` (two call sites; never checked) and `wiki_state` (ingest's wiki state: the model sees the page as empty, and an update drafted against it fails its base-hash check at `promote`). Because an empty read makes the page invisible without a word and `lint._read` (`lint.py:118-122`) reads with `errors="replace"`, the structural linter MUST gain one rule: a wiki page (every file `list_pages` lists, `index.md` and `log.md` included) whose bytes are not valid UTF-8 is a violation reported once, as `<rel>: not valid UTF-8 (<UnicodeDecodeError reason> at byte <start>)`, and the page's other checks are skipped for that run. The rule is fatal like every structural violation: `lint` exits 1 and, because `promote` lints the whole staged wiki, an existing non-UTF-8 page refuses every `promote` (exit 9, nothing written) until it is fixed, related to the patch set or not, with the error naming the page. This is an upgrade break for a wiki that already holds such a page (today it promotes); the 0.8.0 CHANGELOG Upgrade notes MUST carry this text in substance: "0.8.0 adds a structural rule: every wiki page must be valid UTF-8. A wiki that holds a page that is not will fail `lint` and refuse every `promote` until the page is fixed. The error names the page. Remedy: re-encode the page as UTF-8, or remove it and its index entry. Run `wiki-studio lint` before upgrading a wiki's tooling to see whether any page is affected." `api.read_page` already refuses a non-UTF-8 page with exit 4 (`api.py:886-887`) and is unchanged. No frozen fixture has a non-UTF-8 page, so no frozen number moves.
- **FR-004 (eligibility)**: A page is eligible for either ranker when it is linked from `index.md` and accepted by `_extract_index_links(index_md, wiki_dir)` (inside the wiki, no symlink on the way), is a regular file, is valid UTF-8, and does not carry `superseded_by` (D7; `schema.SUPERSEDED_BY_KEY`, judged on the frontmatter of the bytes read in this call). `index.md` and `log.md` are never candidates. Each ineligible linked page is reported once in `FindResult.ineligible` as `{path, reason}` with `reason` one of `missing`, `not-regular-file`, `not-utf8`, `superseded`. Discovery reads each eligible page once per call as bytes (the one read that FR-014 hashes), records its sha256 and byte count, and decodes it for the prompt. For the `index-first` ranker discovery calls `_select_query_candidates(paths, question, max_pages=<number of index-linked candidates>)` so the whole ranked list is returned, drops ineligible paths from that ordered list, then applies the budget and the cap (FR-007); the selector's own read serves ranking only and its body is not edited (this reconciles D7 with finding 2; owner decision, 2026-10-27, on the PR #52 review). On a wiki with no superseded, oversized or non-UTF-8 page the selected pages and their order equal `_select_query_candidates(..., max_pages)` exactly, and a test pins it.
- **FR-005 (documents and the query)**: The FTS5 table has four columns: `path` (the slug and the path segments as words, `-` and `/` replaced by spaces), `title` (the frontmatter `title`), `headings` (every markdown heading line, `#` stripped) and `body` (the page with its frontmatter removed). The tokenizer is a constant (`porter unicode61` untuned; FR-021 tunes it). The question goes through `wiki_state._tokenise` (the querier's token pattern and the frozen stop list); each remaining token is double-quoted with every `"` doubled, and the quoted tokens are joined with ` OR `. Raw question text never reaches `MATCH`; a question that yields no token selects nothing (empty `pages`, no error). Tests MUST pass questions containing `"`, `NEAR`, `AND`, `OR`, `NOT`, `-`, `*`, `:`, `^`, `(`, `)`, `{`, `}` and non-ASCII letters through both rankers and assert that none raises.
- **FR-006 (ranking and the configuration hash)**: FTS5 ranking is `bm25(pages, <w_path>, <w_title>, <w_headings>, <w_body>)` with the four weights from the ranker configuration: `RankerConfig`, a frozen dataclass in `discovery.py` (`tokenizer`, `weights`, `min_match_tokens`, `max_pages`), whose live default `DEFAULT_RANKER_CONFIG` is the untuned `porter unicode61`, `4.0, 4.0, 2.0, 1.0`, `1`, `5` until FR-021 replaces it with the tuned one; `api.find` and `api.query` take an additive `ranker_config: RankerConfig | None = None` (`None` is the live default), so the evaluation runner can run any committed configuration without editing code, and a configuration's hash keys the cache (FR-013) so two configurations never share an index, ascending by the bm25 value (SQLite returns a lower value for a better match), ties broken by index position (the page's first occurrence in `index.md`), then the cap of `max_pages` (at most 5 through `api.find`, `api.query`, the CLI and the MCP tool; `DEFAULT_MAX_QUERY_PAGES` stays 5). An optional minimum-match rule, `MIN_MATCH_TOKENS` (the number of distinct question tokens a page must match to be selected, default 1, which is no rule; FR-021 may set it to 2), discards pages below it before the cap. `ranker_config_hash()` MUST be the lowercase hex SHA-256 of the canonical JSON (sorted keys, separators `,` and `:`, UTF-8) of `{"ranker": "fts5", "tokenizer": <str>, "weights": [<4 floats>], "min_match_tokens": <int>, "max_pages": 5}`; it keys the cache (FR-013) and is frozen before the held-out run (FR-028). Every result and every evaluation record carries it. No learned ranking, synonyms, query expansion, embeddings or model reranking.
- **FR-007 (the byte budget, D6)**: `max_bytes` counts the UTF-8 bytes of `index.md` plus the selected pages; the default is `DEFAULT_MAX_CONTEXT_BYTES` (65,536). Pages are taken in rank order after eligibility and the minimum-match rule; a page that does not fit is skipped, listed in `FindResult.omitted` as `{path, bytes}`, and the next page is tried; selection stops when `max_pages` pages are selected or the ranked list is exhausted; pages are never truncated. If `index.md` alone exceeds the budget, no page is loaded, `pages` is empty and `warnings` carries one message saying so. `max_bytes` must be a positive integer (`ValueError` otherwise, CLI exit 1 as for any rejected flag value). The budget applies to both rankers in `api.find` and `api.query`; the frozen runs call the selector directly and have no budget. The default never binds on the current fixtures (run 2's five largest pages total about 38 KB), so it is a ceiling for oversized pages, not a tuned value.
- **FR-008 (API, additive with defaults)**: `api.find(question, paths, *, max_pages=DEFAULT_MAX_QUERY_PAGES, max_bytes=DEFAULT_MAX_CONTEXT_BYTES, ranker: str | None = None, ranker_config: RankerConfig | None = None) -> FindResult`; `ranker=None` means `resolve_ranker(None)` (environment, then default); `ranker_config=None` means `DEFAULT_RANKER_CONFIG` (FR-006). `FindResult` gains, as last fields with defaults, `ranker: str`, `fallback_reason: str | None`, `bytes_loaded: int`, `max_bytes: int`, `omitted: tuple[OmittedPage, ...]`, `ineligible: tuple[IneligiblePage, ...]`, `ranker_config_hash: str | None` (None for `index-first`) and `warnings: tuple[str, ...]`; `FoundPage` gains `sha256: str` and `bytes: int` (lowercase hex SHA-256 and length of the bytes read in this call). `api.query` gains `max_bytes: int = DEFAULT_MAX_CONTEXT_BYTES` and `ranker: str | None = None`; `DefaultQuerier` gains `max_bytes` and `ranker` fields with the same defaults and selects through `discovery.select(...)` instead of calling `_select_query_candidates` directly; the prompt and the citation check (`validate_citation_evidence`) still use the text read in this call, never the cache, and the query-log line gains `ranker` and `bytes_loaded` beside its existing keys. `api.find` keeps raising `SourceMissingError` (exit 5) when the wiki has no `index.md`. Every new parameter is keyword-only with a default, so its position carries no compatibility meaning.
- **FR-009 (CLI)**: `find` and `query` gain `--ranker {fts5,index-first}` and `--max-bytes N`. The ranker is `resolve_ranker(args.ranker)`: the flag overrides `WIKI_STUDIO_RANKER`, which overrides the shipped default, as every other setting does. `find --json` MUST print, beside its 0.7.0 keys (`question`, `index`, `pages[].path/file/title`), the keys `ranker`, `fallback_reason`, `bytes_loaded`, `max_bytes`, `ranker_config_hash`, `omitted`, `ineligible`, `warnings`, and `sha256` and `bytes` on each page; the text form prints the ranker on the first line and each page's byte count. When FTS5 is missing and the ranker was `fts5`, one notice goes to stderr (`find: FTS5 is not available in this Python's SQLite (<reason>); using index-first`); the exit code stays 0. A bad `--ranker` or `WIKI_STUDIO_RANKER` value is a `ValueError` (exit 1, `cli.py:_report`).
- **FR-010 (contract)**: `api.info` and `info` (text and `--json`) MUST gain a `discovery` key: `fts5` (bool), `sqlite_version`, `fts5_reason` (null when available), `default_ranker` and `default_ranker_source` (`env` or `default` for the CLI and `api.info`; `flag` only in the MCP `info` tool when the server was launched with `--ranker`, FR-035; owner decision, 2026-10-27, on the PR #52 review), `ranker_config_hash`, and `cache` (`path`, `state`: `present`, `missing` or `unusable` with a `reason`; from US2, `null` until then). Two new capabilities with resolvers in `tests/test_info_contract.py`: `ranked-discovery` (resolves when `api.find` has a `ranker` parameter and `discovery.fts5_available` is callable) and `context-budget` (resolves when `api.find` and `api.query` have `max_bytes`). Every 0.7.0 `info` key keeps its name and meaning. `docs/knowledge-contract.md` gains a Discovery section (the keys above, the eligibility rule, the budget rule, the fallback) and `README.md` documents `--ranker`, `--max-bytes`, `WIKI_STUDIO_RANKER` and the fallback notice.
- **FR-011 (US1 tests)**: Tests MUST pin: with the probe patched false, `find --ranker fts5` falls back with the notice, `ranker: "index-first"`, a non-null `fallback_reason`, exit 0, and `pages` equal to `_select_query_candidates`'s selection; the operator questions of FR-005 never raise; a superseded page is never selected by either ranker and is counted `superseded`; an oversized-page fixture covers skip-and-continue (`omitted` names it, the next page is selected) and an index over budget (no page, one warning); a non-UTF-8 page fixture: `find` with either ranker skips and counts it `not-utf8`, `lint` reports exactly one violation naming its path, `lint --health` and `lint --prose` complete without raising, an unrelated promote (a patch set that only appends to `log.md`) is refused with exit 9 and an error naming the page, and the same promote succeeds once the page is re-encoded; the cap and the tie order hold (a fixture where two pages score equally selects them in index order); a link to a symlinked page or through `../` is never a candidate; `find` and `query` leave the wiki tree byte-identical (a tree hash before and after); `find --json` carries every FR-009 key; `WIKI_STUDIO_RANKER` and `--ranker` precedence; `info --json` has `discovery` with `fts5`, `sqlite_version` and `default_ranker_source`; and `tests/test_navigation_eval.py` stays green unchanged.

### US2 — the rebuildable cache

- **FR-012 (location, D1)**: The cache file is `<resolved-wiki-parent>/.<wiki-dir-name>.wiki-studio.search.sqlite`, beside the lock file, derived from the resolved wiki as `wikilock.lock_path_for` derives the lock (`SEARCH_CACHE_SUFFIX = ".wiki-studio.search.sqlite"` beside `LOCK_FILE_SUFFIX`; `search_cache_path_for(wiki_dir)` in `paths.py`). `WikiPaths` gains `search_cache: Path | None = None` (an explicit override; `None` means derive at use) resolved in `paths.py` by `--search-cache` (a new common flag) and `WIKI_STUDIO_SEARCH_CACHE` (`ENV_SEARCH_CACHE`) with the existing flag, variable, default precedence; `WikiPaths.resolve` and `for_root` refuse an explicit path that resolves inside the wiki directory with `ValueError` naming both paths, which the CLI reports as exit 1 (the CLI's one rule for a rejected flag value, `cli.py:_report`, as `--lock-timeout -1`; the pitch said exit 2, the code says 1, and the code wins), and `search_index` re-checks at open and raises `ContractViolationError` (exit 4) for a `WikiPaths` built directly with such a path (owner decision, 2026-10-27, on the PR #52 review). The single-writer rule needs no exception because the cache is not in the wiki: `search_index.py` is the only module that opens the cache for writing, a test asserts the package names `SEARCH_CACHE_SUFFIX` and `sqlite3.connect` only there, and the FR-016 behaviour test covers what the syntactic scans cannot. One `.gitignore` pattern, `.<wiki-dir-name>.wiki-studio.*`, covers the lock and the cache; `README.md` (Layout) and `docs/consumers.md` say so. `info` reports the path and state under `discovery.cache` (FR-010).
- **FR-013 (content manifest and meta)**: The cache holds a `manifest` table (`path TEXT PRIMARY KEY`, `sha256 TEXT`, `bytes INTEGER`), the FTS5 table `pages` (FR-005, with `path` as an unindexed column that joins the manifest), and a `meta` table (`key TEXT PRIMARY KEY`, `value TEXT`) with `cache_format`, `ranker_config_hash`, `wiki_path` (the resolved wiki directory), `wiki_id` (the manifest's when the wiki has one, else the empty string), `sqlite_version` and `package_version`. `PRAGMA user_version` carries `CACHE_FORMAT = 1`. Page text is stored only in the FTS5 table for ranking and MUST NOT be read back for a prompt. That table therefore holds a full copy of every eligible page's text in a file beside the wiki: `SECURITY.md` says so (FR-042), and FR-015 creates the file readable by its owner only.
- **FR-014 (refresh on every call, D2)**: Every `find` and `query` under the `fts5` ranker MUST, under one `BEGIN IMMEDIATE` transaction with `busy_timeout` set to `SEARCH_CACHE_BUSY_TIMEOUT_SECONDS = 5` (owner decision, 2026-10-27, on the PR #52 review): read `index.md`, compute the eligible set (FR-004), read and hash each eligible page (the reads of FR-004, no extra I/O), and diff against `manifest`: a new path is inserted into both tables; a changed sha256 is replaced; a path that is gone, unlinked, now superseded or now non-UTF-8 is deleted from both; a rename is a delete plus an insert. No mtime, size or stat shortcut is ever used. Ranking then runs in the same transaction over the current paths only, so the cache can never return a page the wiki no longer has. The text given to the prompt comes from this call's reads, never from the cache.
- **FR-015 (recovery, D3)**: `search_index.py` creates the cache file with `os.open(path, O_CREAT | O_EXCL | O_NOFOLLOW, 0o600)` and closes it before SQLite opens it, so the copy of the page text is no more readable than the wiki (on Windows the directory's default ACL applies); a POSIX test asserts mode `0o600` after creation and after a rebuild. On open, a `meta` whose `cache_format`, `ranker_config_hash`, `wiki_path` or `wiki_id` differs from the current values, or a `user_version` other than `CACHE_FORMAT`, drops the three tables and rebuilds them in the same call. The cache marks itself with `PRAGMA application_id` (`CACHE_APPLICATION_ID`), and only a file that is empty or carries that id in its SQLite header is ever rebuilt, removed or tightened: a `sqlite3.DatabaseError` on open or read (a truncated or garbled cache whose header still carries the id) removes the cache file and rebuilds it, but only when the path is a regular file (`lstat`, not a symlink) outside the wiki; a file that is neither empty nor so marked (a text file, another program's database, a cache whose header is gone) is left untouched, byte for byte and mode included, and the call ranks in memory with one warning naming the manual reset (owner decision on the PR #56 review, 2026-10-27: an explicit `--search-cache` pointing at an unrelated file must never destroy it). A symlink at the cache path or at its parent, an unwritable parent directory, a read-only file system, or a lock held past the busy timeout makes this call use an in-memory index with one warning in `FindResult.warnings` and on stderr; the symlink's target is never opened, read or removed (SQLite opens paths itself and follows symlinks, so the `lstat` check precedes every open and the remaining check-then-open window is outside the wiki boundary and touches only derived data, which `SECURITY.md` states). Missing or broken cache state never makes `find` or `query` exit non-zero. Deleting the file is the documented manual reset (`README.md`).
- **FR-016 (the wiki stays byte-identical)**: A behaviour test MUST hash the whole wiki tree (every file's path and bytes, symlinks included by target) before and after every US1 and US2 case and assert equality, and assert that no file under the wiki directory was created, since the syntactic single-writer scans (`tests/test_e2e.py:1054-1092`, `tests/test_audit.py:466-508`) would not notice a `sqlite3.connect` under the wiki. Those scans stay green and unchanged.
- **FR-017 (cache recovery tests)**: `tests/test_search_index.py` MUST cover, each through `api.find` and the CLI with the cached ranking compared to a fresh in-memory ranking (`search_index.build_in_memory`): a hand edit of a page with the same size and a restored mtime (`os.utime`); a `git checkout` of an older revision in a temporary repository; a rename; a delete; a page unlinked from the index; an `index.md` edit that reorders links (tie order follows); a page that gains `superseded_by`; a truncated cache file; a cache of random bytes; a wrong `user_version`; a changed `ranker_config_hash`; a cache copied from another wiki (different `wiki_path` and `wiki_id`); a symlink at the cache path (its target untouched, in-memory fallback with the warning); a read-only parent directory (fallback with the warning); two processes refreshing at once (subprocesses, both exit 0, identical selections); a process killed during a refresh (`SIGKILL` inside the transaction via a patched step in a subprocess bootstrap), after which the next call is consistent; a property test that after any random sequence of these operations (seeded, at least 200 steps) the cached ranking equals a fresh in-memory ranking; and FR-016's byte-identity assertion in every case.
- **FR-018 (measured, not assumed)**: `info.discovery.cache.state` reports `present`, `missing` or `unusable` with the reason. FR-020's latency block reports the cached path beside a fresh in-memory build with no cache so the cache's value is a number; S2 ships whatever that number says, because the roadmap requires cache recovery tests, and a cache that does not pay on small wikis is reported as such in the README Evidence section.

The call is `api.promote(proposal_dir, paths, dry_run=..., entry_point=PROMOTE_ENTRY_POINT_MCP, by=LAUNCH_BY)` (`LAUNCH_BY` as in FR-035); `allow_out_of_repo`, `allow_unguarded_updates` and a caller-chosen `entry_point` are never passed. `promoter.py` gains `PROMOTE_ENTRY_POINT_MCP = "mcp"` beside `_API` and `_CLI`, the receipt records it as `promoter.entry_point` (an additive value; `receipt_version` stays 1), and `docs/patch-set-format.md` lists it.
- **FR-040 (errors and clean stdout)**: Every `wiki_studio.errors.IngestError` subclass and `ValueError` raised by a tool MUST become a tool error result (`isError: true`) whose content is the JSON `{error: <class name>, exit_code: <errors.py's code, 1 for ValueError>, message: <str>}`; anything else becomes `{error: "InternalError", exit_code: 1, message: <class name only>}` with no traceback or path in the message. stdout carries protocol frames only; every log line goes to stderr (Python `logging` configured to stderr at launch, and `warnings` redirected there). `tests/test_mcp_adapter.py` MUST drive every tool through a subprocess over stdio with the SDK's client, including each error class, and fail on any stdout byte that is not part of a protocol frame.
- **FR-041 (the trace file)**: With `--trace PATH` the server appends one JSON line per request to `PATH`: `ts` (UTC ISO 8601), `method` (`initialize`, `tools/list`, `tools/call`), `tool` (the tool name or null), `protocol_version` (negotiated), `client_name`, `client_version`, `outcome` (0, or the error result's `exit_code`), `duration_ms`. Page content, question text, edit content and file paths MUST NOT be traced. The file is opened append-only, outside the wiki (a path inside the wiki is a launch error, exit 2), and an unwritable trace path is a launch error, never a silent drop. Opt-in only; without the flag nothing is written.
- **FR-042 (adapter docs)**: `docs/mcp-adapter.md` MUST cover the install (`wiki-studio[mcp]`), the launch flags and variables, the tools with their arguments and results, the boundary (what is not exposed, `--disable-tool`, propose-only mode, the fixed actor, auto-approval by policy, errors), the host configuration for Claude Code (`claude mcp add wiki-studio -- wiki-studio-mcp --root …` and `.mcp.json`) and Kiro (`.kiro/settings/mcp.json`), the trace file, and what the adapter does not do. `SECURITY.md` gains one paragraph on the agent surface (the eight tools, no root argument, the fixed actor, auto-approval by policy) and one on the search cache: it holds a full copy of every eligible page's text beside the wiki, it is created owner-only (FR-015), and it has the check-then-open window FR-015 describes. `README.md` gets an MCP section pointing to the doc.

## Constraints

- **Standard library in the core.** `sqlite3`, `hashlib`, `json`, `os`, `posixpath`, `uuid` and `pathlib` suffice for US1..US3; the only optional dependency is `mcp>=2.3,<3` behind `wiki-studio[mcp]`, imported only under `src/wiki_studio/mcp_adapter/`, and FR-033 proves the base install imports nothing outside the standard library.
- **Contracts.** Exit codes 0 and 2..11 keep their meaning and 1 stays fatal lint (and a rejected flag value); no new exit code (a missing FTS5 or a broken cache is never an error; refusals map to 4, 5, 7, 9 and 1 for a rejected value). `api` changes are additive with defaults; existing `info --json` keys keep their names and meaning; the receipt stays version 1 with `entry_point: "mcp"` an additive value; the patch-set format is unchanged.
- **The page schema does not change.** No new frontmatter key, page type or directory; ADR-0002 is untouched; ADR-0003 records the optional dependency and the tool contract.
- **Single writer.** `promoter.py` stays the only module that writes into the wiki directory; the cache lives outside the wiki (D1) and `search_index.py` is its only writer; the single-writer scans stay green and FR-016 adds the behaviour test.
- **No model call** in `findings`, `review_state`, the MCP `lint` tool or `find`; the MCP surface spawns no model.
- **No reentrant `WikiLock`;** `find` and `query` take no wiki lock (read verbs, as today).
- **Frozen evidence.** The files of FR-019 are never edited and a test pins their sha256; the held-out ingest runs once; tuning happens only on the development set after the held-out freeze; the held-out run happens once after the configuration hash is frozen.
- **Out of scope (no-gos).** Hosted collaboration, a new runtime, a required vector store or embeddings, mandatory semantic judges, prose auto-rewrite, crash-safe multi-file transactions; learned ranking, synonyms, query expansion, model reranking; MCP resources, prompts, HTTP or SSE transport, authentication; `approve`, `ingest`, `query`, `audit-flush` or `init` on the MCP surface; an adapter override of the approval policy; registry publication (a launch step after Release C closes); the memkernel quickstart and the memkernel integration measurement; the standalone quickstart of Release B.
- **Python 3.11–3.13;** FTS5 availability is probed at runtime, never assumed; the SQLite version is recorded in every result.
- **Gate.** `poetry run ruff check src/ tests/ eval/ && poetry run ruff format --check src/ tests/ eval/ && poetry run mypy src/ && poetry run pytest -q -p no:cacheprovider --cov=wiki_studio --cov-fail-under=92` stays green; coverage does not fall below 92%; both frozen evaluation runs' determinism tests and the sha256 pins stay green.
