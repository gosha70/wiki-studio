## Why

A wiki page cites its evidence as `path:` + `sha:`. When the cited file later
changes in place, nothing tells the curator: `stale-claim` checks only that the
path exists, and `citation-rules.md` calls drift "a curator pass". The issue 54
study measured the gap on 24 such sources: `stale-claim` flagged none,
including the one page that needed review; a plain "did the file change since
its `sha:`" check flagged 13 pages, of which one was a true review and twelve
were false alarms, and it surfaced one real citation error (the
judge-statistics page cites `spearman.py` at a commit that does not contain
it). Issue 120 asks for a specification that fixes what a flag means, how the
false flags are cut or explained, what the check costs, where it runs, and what
happens when a `sha:` is missing or unknown.

This bundle does it in two runs. The evidence run (US1-US3) labels seven real
review cases from code-copilot-team's history beside the study's 24 sources,
freezes the labels, the candidates and the bar after the owner reviews the
labelling commit, and measures five model-free candidate filters, publishing
the result whatever it shows. The build run (US4-US8) ships, inside
`findings` only, an exact citation-error kind `source-not-at-revision` over a
hardened read-only git layer that looks in the root's repository and the
configured source roots, a `revision_check` result that says when the check
could not run, and, only if a candidate cleared the frozen bar,
`source-revision-changed`, a finding that flags and still returns. Nothing
changes in `lint`, `lint --health --strict`, `stale-claim`, approvals, `find`,
the page schema, the exit codes, the MCP tool set or the dependency list, and no
model is on any path from `findings`, `approve` or `review_state`.

### US3 — the measurement and its recommendation (S2)

### US4 — the hardened read-only git layer (S3)

- **FR-017 (the module and its command set, finding 16, no-gos)**: A new module `src/wiki_studio/revisions.py`, standard library only, holds every git call the revision check makes; `findings.py` reaches git only through it. Every call is `subprocess.run` with an argument list (never a shell), `capture_output`, the environment of FR-018 and the timeout of FR-022, and the prefix `git --no-pager -c core.fsmonitor=false -c core.hooksPath=<os.devnull> -c protocol.allow=never -C <dir>`. The module enforces in code an allowlist of exactly FR-008's p1-p7 shapes (p5-p7 present only when FR-031 ships a candidate that needs them): `rev-parse` with `--show-toplevel --is-shallow-repository HEAD` or `--verify <commit-ish>^{commit}`; `config --get extensions.partialclone`; `diff-tree -r --name-status --no-renames --relative --no-ext-diff --no-textconv <commit> <commit> -- <paths>`; `diff --no-ext-diff --no-textconv` between two commits (`--quiet`, `-U0`, `-w --ignore-blank-lines`) followed by `-- <path>`; `cat-file blob <commit>:./<path>`. A request outside it raises before any process starts. No command reads the index or the working tree, writes, fetches, or overrides `safe.directory`.
- **FR-018 (a clean environment for every call, D20)**: Each call's environment is built from `os.environ` with every variable whose name starts with `GIT_` removed, except `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` (named once, in a constant), then `GIT_CEILING_DIRECTORIES` (FR-019), `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C` set. System and global config are kept, never ignored. `paths.git_toplevel` is unchanged and is not used by the revision layer.
- **FR-019 (the repository list and its classification, D6, D7, D9)**: The list is the root's repository, then each source root in configured order (`--source-root`, else `WIKI_STUDIO_SOURCE_ROOTS`, the flag replacing the variable, as `WikiPaths.resolve` does). Each is classified once per run by p1 and p2. The root's repository is its git toplevel, as today (`--root` may name a subdirectory): p1 runs from the root with no ceiling, and its later calls set `GIT_CEILING_DIRECTORIES` to the resolved toplevel's parent. A source root's calls set `GIT_CEILING_DIRECTORIES` to its resolved parent, and it is used only when p1's toplevel, resolved, equals the configured directory, resolved. Reasons, each a named constant, recorded verbatim in `revision_check`: `not a git work tree`, `not the top of a git work tree`, `shallow clone`, `partial clone`, `refused by git: repository ownership` (never forced), `no HEAD commit`, `git call timed out` (the repository is skipped for the rest of the run) and `git call limit (<N>) reached`. A usable repository's HEAD is p1's full commit. Git missing from PATH (`OSError` on the first call) makes the state `off`, reason `git not found`, with no further call. A skipped repository is never fetched into or written to.
- **FR-020 (validating a `sha:` and a path)**: A `sha:` reaches git only as 7-40 lowercase hex characters (`SHA_MIN_LENGTH = 7`, `SHA_MAX_LENGTH = 40`, fixed internal constants): a lowercase-hex value shorter than 7 is *not checked*, reason `too short`, no finding; any other non-conforming value (uppercase, non-hex, longer than 40, option-shaped such as `--output=x`) is `source-not-at-revision` (malformed) with no git call. A `path:` must be relative and stay inside the matched directory after `posixpath.normpath` (no absolute path, no leading `..` component, no NUL); otherwise the source is *not checked*, reason `path outside <dir>`, no finding (O7). A path reaches git only after `--` or as `<commit>:./<path>`. After a match, every later call uses p3's full 40-hex commit, never the short `sha:`.
- **FR-021 (matching and the ambiguity rule, D6, D20, the pitch review's note 2; O2)**: For each distinct `sha:`, repositories are probed in list order with p3, `git rev-parse --verify <sha>^{commit}` without `--quiet`, so git's own commit-typed lookup decides: exit 0 with one 40-hex line means the repository has that commit (a non-commit object sharing the prefix does not make it ambiguous); stderr is classified in this order, the first match winning: a non-zero exit whose stderr (under `LC_ALL=C`) contains `is ambiguous` (checked first, because for an ambiguous prefix git prints both `short object ID … is ambiguous` and then `Needed a single revision`, exit 128, while a missing commit prints only the second) means the prefix is ambiguous among commits there: the source is *not checked*, reason `ambiguous in <repo>`, the search stops and no later repository is consulted, and it never yields `source-not-at-revision`; otherwise, a non-zero exit whose stderr contains `Needed a single revision` means the repository does not have it, and the search moves on; any other failure skips that repository with its message (no finding is derived from it). The first usable repository that has the commit is the source's repository and is named. With no match: when every repository in the list was usable and none reported an ambiguity, the source is `source-not-at-revision` listing the repositories searched; when at least one was skipped, it is *not checked*, reason `commit not found in the usable repositories`, no finding.
- **FR-022 (the per-run call cap and the timeout, the pitch review's note 3; O3)**: `WikiPaths` gains `git_call_limit: int = DEFAULT_GIT_CALL_LIMIT`, resolved from `WIKI_STUDIO_GIT_CALL_LIMIT` (`ENV_GIT_CALL_LIMIT`, beside `ENV_LOCK_TIMEOUT`) as the lock timeout is: a non-negative integer, anything else `ValueError` (exit 1, as an invalid lock timeout today). The default is configuration, not a magic number: `DEFAULT_GIT_CALL_LIMIT` is defined once in `paths.py` beside `DEFAULT_LOCK_TIMEOUT`, its value is S2's recorded process count for the shipped call plan on the study run (`results/candidates.json` `process_counts`: the exact kind's plan, plus the winner's steps when FR-031 names one; with C2, `with_candidate.C2`, 50 processes, unchanged by FR-032's anchor rule) times the headroom 10, rounded up to the next multiple of 100 (500), and its comment names the recorded count and the headroom. The per-call timeout `GIT_CALL_TIMEOUT_SECONDS` in `revisions.py` is the slowest recorded call times the same headroom, rounded up to whole seconds, at least 10 (0.012 s recorded, so 10). `tests/test_revisions.py` recomputes both from the committed results file and asserts the constants equal them. Every git call counts toward the cap; when it is reached no further git call runs, every source not yet checked is *not checked* with reason `git call limit (<N>) reached`, and none of them is a finding.
- **FR-023 (batching)**: Calls follow FR-008's plan: each repository classified once; each distinct `sha:` probed in order until the first match or ambiguity; one p4 per matched (repository, commit), whose statuses decide the exact kind (`A`: absent at the `sha:`, present at HEAD) and the structural rule (`D`: absent at HEAD, no revision kind) and mark `M`/`T` paths as changed; a cited path absent from p4's output is unchanged or absent at both commits, no finding either way. Process count therefore grows with repositories times distinct commits, not with sources. Paths are read relative to the matched directory (the root, or the source root), including when `--root` names a subdirectory of its repository.
- **FR-024 (US4 tests)**: `tests/test_revisions.py` (EGOGE header), on temporary git repositories built by the test (skipped unless `git` is on PATH; CI runs them): classification of a full clone, a plain directory, a shallow clone, a partial-clone configuration, a subdirectory of a repository given as a source root (skipped, `not the top of a git work tree`, its commits never matched) and a root that is a subdirectory of its repository (used), with a cited file added under that subdirectory after its `sha:`: exactly one `source-not-at-revision`, which fails without p4's `--relative`;
