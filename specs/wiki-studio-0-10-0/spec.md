## Why

wiki-studio can say what is wrong with a wiki (`lint`, `findings`), but
nothing runs those checks unattended and nothing drafts a fix while the
curator is away. Issue #70 asks for that run with one condition: it prepares
and stops. It may draft proposals into the proposals directory; it never
promotes or approves, and a curator reviews what it drafted with the
existing commands.

This release adds one verb, `wiki-studio nightly`, over existing pieces. It
runs structural lint with the audit-format pass and `findings`, and writes
one report. With an explicit `--backend` it creates at most five proposals,
with at most ten model calls, for two kinds whose fix is "add a link" (`missing-cross-link`, and a
`weak-orphan` not linked from the index), each refused unless a syntactic
check shows it adds links and changes nothing else, each bound to the bytes
it was drafted from by `base_sha256`, and each written through
`api.propose` under a deterministic name, so a rerun creates no duplicate.
A cron and CI recipe is documented and checked, the curator persona says a
person approves a `nightly-*` draft, and the change ships as 0.10.0 with a
`nightly` capability and format version in `info`. Nothing else moves: no
change to `findings`, `lint`, `promoter.py`, the page schema, the patch-set
format, the exit-code meanings, the MCP adapter or the dependency list, and
no model on any path from `findings`, `approve` or `review_state`.

## User Scenarios

### US1: The pass and its report, model-free (Priority: HIGH)

**Given** a clean wiki, a wiki with health and review findings, and a structurally broken wiki, with no backend installed and backend resolution patched to fail
**When** `api.nightly(paths)` runs on each
**Then** each run returns a result whose markdown report has the fixed sections in order, lists lint violations and audit errors, the findings with counts by kind, and what needs a curator including the pending proposal directories; the broken wiki's result says lint failed with violations first and still lists the findings; no lock file appears beside the wiki, no directory appears under the proposals directory, every file under the wiki directory (`.audit/` included) has the same sha256 before and after, and a report path that resolves inside the wiki (directly or through a symlinked directory) is refused before anything runs

### US2: The verb on the CLI contract (Priority: HIGH)

**Given** the same wikis
**When** `wiki-studio nightly`, `nightly --json` and `nightly --report PATH` run through `cli.main`
**Then** the markdown goes to stdout or to PATH (written atomically), `--json` prints the result object, a broken wiki exits 1 after writing the report, an unwritable report exits 6 with the reason on stderr even when lint also failed, `nightly --help` lists the flags, the top-level help lists the verb, `wiki-studio nightly` is not read as a legacy single-source ingest, and `nightly.py` neither imports `promoter` nor names `promote` or `approve`, and a run with every promote and approve entry point patched to raise completes

### US3: Drafting with an explicit backend (Priority: HIGH)

**Given** a wiki with a `missing-cross-link` finding and a `weak-orphan` linked from a content page only, and the test backend or a stub backend
**When** `wiki-studio nightly --backend test` runs, and runs again with stubs that fail, answer invalid JSON, or over-reach (a reworded sentence, a "See also" line, a changed frontmatter line, a second index link)
**Then** each draftable finding gets its own proposal directory `nightly-<kind>-<key>` written by `api.propose` with every `update` carrying the `base_sha256` of the `api.read_page` bytes the prompt showed, the wiki directory is byte-identical before and after, each created proposal promotes cleanly and clears its finding, each over-reaching draft is refused by the link-only check with no directory written and exit 4, a backend failure on one finding does not stop the next, a lock timeout or a failed proposal write stops drafting and the report says so for every remaining finding, `--max-proposals N` caps the proposals created at N and the backend calls at 2×N, a finding that always fails does not block later ones, `--max-proposals 0` makes no backend call, `WIKI_STUDIO_BACKEND` and PATH auto-detect are never consulted, and the exit code follows FR-010's precedence

### US4: No duplicate on rerun (Priority: HIGH; cut together with US3 only)

**Given** a wiki where a run already created its proposals
**When** the pass runs again on the unchanged wiki, after a proposal was archived to `.applied/`, after a curator deleted one, and while another run creates the same directory
**Then** the unchanged rerun creates no directory and makes no backend call, an archived or deleted proposal is drafted again while its finding persists, and two overlapping runs leave one directory and report "already proposed"

### US5: The recipe and the guidance (Priority: MEDIUM)

**Given** `docs/nightly.md`, the packaged persona and the packaged `ingest-rules.md`

### US6: Release 0.10.0 and closure (Priority: MEDIUM)

**Given** the five phases above landed, or cut by the circuit breaker in the pitch's order

## Requirements

### US1 — the pass and its report, model-free

- **FR-001 (module and entry point)**: A new module `src/wiki_studio/nightly.py` holds the pass, its result type and the report rendering. `api.nightly(paths: WikiPaths) -> NightlyResult` is the library entry (US3 adds keyword arguments with defaults, FR-013). The pass calls `api.lint(paths)` (no health tier, no prose, not strict) and then `api.findings(paths)` (`pages=None`); it takes no wiki lock, resolves no backend (FR-013 owns when one is resolved), and constructs no `WikiLock` anywhere. An exception raised by `api.lint` or `api.findings` (for example a newer manifest, exit 4) ends the run with that error's exit code and no report, as `findings` itself does. `nightly.py` imports only the standard library and `wiki_studio`; it calls the `api` functions it uses through a deferred import to avoid an import cycle with `api.py`. Every behaviour of the pass is in this module; `cli.py` parses, calls `api.nightly`, renders and writes (FR-005, FR-009).
- **FR-002 (the result and its JSON form, D8)**: `NightlyResult` is a frozen dataclass; `as_dict()` returns the JSON object `--json` prints, with these keys (read by name, order carries no meaning): `nightly_version` (1, from a constant `NIGHTLY_FORMAT_VERSION = 1` in `contract.py` beside `FINDINGS_FORMAT_VERSION`; FR-033 advertises it), `package_version`, `run_at` (UTC, ISO 8601 to the second with `Z`), `wiki_dir` and `proposals_dir` (resolved, as strings), `lint` (`passed`, `violations`, `audit_errors`), `findings` (exactly `api.findings(paths).as_dict()`), `drafting` (`state`: `off` | `skipped` | `on` | `stopped`, `reason` or null, `backend` or null, `max_proposals` and `max_attempts` (FR-016's two bounds) or null, `attempts` (backend calls made) and `created` (proposals created) as integers; US3), `proposals` (`created`, `already_proposed`, `not_drafted`, `failed`, each a list; US3 and US4, entries per FR-022), `needs_curator` (`findings`: the finding objects of FR-003(a) and (b); `pending`: FR-006's entries), `warnings` (managed-drift messages, FR-020) and `exit_code` (FR-010, the final code including a report-write failure). `NightlyResult.exit_code` is FR-010's code without the report-write case, which the CLI applies (FR-005).
- **FR-003 (the markdown report, fixed headings)**: `NightlyResult.render_markdown()` returns markdown with these headings, in this order: `# wiki-studio nightly report`; a header list naming the run time (UTC), the resolved wiki directory, the resolved proposals directory, the package version and (US3) the drafting state and reason of FR-022; `## Lint` (passed, or each structural violation, then each audit-format error, or "clean"); `## Findings` (the non-zero counts by kind, then one line per finding in `findings` order, `[<kind> / <severity>] <pages>: <description>` as `findings`' text form prints it, or "none"); `## Proposals` (US3, FR-022); `## Needs a curator` with `### Findings`, listing (a) every finding the pass never drafts (FR-014's report-only set) and (b) every draftable finding for which this run neither created a proposal nor found one pending (drafting off or skipped, either bound or an overlap of FR-016, a failure or drafting stopped of FR-021), each as `[<kind>] <pages>`, and `### Pending proposals` (FR-006). An empty part says "none". Before US3 there is no drafting, so every finding falls under (a) or (b). The report names no secret or environment value.
- **FR-004 (when structural lint fails, D10)**: When `lint.passed` is false (a structural violation; audit-format errors alone do not fail it, `api.py` 233-243), the result still carries the findings, the `## Lint` section lists every violation, nothing is drafted (US3 records `drafting.state = "skipped"`, reason `structural lint failed`, FR-022), and the exit code is 1 by FR-010. Audit-format errors are reported and never stop drafting.
- **FR-005 (where the report goes, D8)**: `nightly.check_report_path(report, paths) -> Path` resolves the given path fully (`Path(report).resolve()`, every existing symlink followed) and raises `ValueError` (exit 1 by `cli._report`) when the result is the resolved wiki directory or lies inside it, as `--search-cache` is refused (`paths.py` 144-146); the CLI calls it before `api.nightly`, so a refused path runs nothing and writes nothing. `nightly.write_report(text, path)` writes UTF-8 to a temporary file created in the resolved path's directory (parents created), then `os.replace`s it onto the resolved path, replacing an existing file; on any `OSError` it removes the temporary file and re-raises. CLI behaviour: with `--report PATH` the markdown goes to that file and not to stdout; without it the markdown goes to stdout; `--json` prints `as_dict()` to stdout instead of the markdown on stdout, so `--report PATH --json` writes the file and prints the JSON. The file is written before the JSON is printed, so the JSON's `exit_code` is final. A report that cannot be written prints `error: could not write the report to <path>: <reason>` on stderr and exits 6 (FR-010). The write line names no `wiki_dir` (the single-writer scan, `tests/test_e2e.py` 1054-1093).
- **FR-006 (pending proposals, cut 1)**: At the end of the run the pass lists every directory directly under the proposals directory whose name does not start with `.` (so `.applied/` is excluded, `paths.py` 74), sorted by name, each with the number of entries in its `plan.json` `edits` list, or `edits unknown` when `plan.json` is missing or unreadable. A missing proposals directory lists none. Reading only; JSON entries are `{"name", "edits"}` with `edits` an integer or null.
- **FR-007 (no write under the wiki, D20)**: A run writes nothing under the wiki directory, `.audit/` included: no page, no ingest-log record, no approval record, no search cache; it creates no lock file (the lock is taken only inside `api.propose`, FR-020). Its only writes are the report file (FR-005) and, with drafting, proposal directories through `api.propose` (FR-020). Proved per phase by a snapshot of every file under the wiki directory (relative path and sha256) taken before and after each run in the tests and compared whole.
- **FR-008 (US1 tests)**: `tests/test_nightly.py`, unittest style with the EGOGE / Apache-2.0 header, building wikis with `tests.conftest.make_repo_layout`: (a) a clean wiki: every part says none, `exit_code == 0`; (b) a wiki with a stale claim, a weak orphan, a missing cross-link and unapproved pages, no backend: the report lists them, no directory appears under the proposals directory, `exit_code == 0` (issue #70's first acceptance line as the pitch carries it); (c) a structurally broken wiki (an orphan page): violations listed, findings still listed, `exit_code == 1`; (d) `check_report_path` refuses a path inside the wiki and a path outside it whose parent is a symlink to a wiki subdirectory, and accepts a path outside; `write_report` creates parents, replaces an existing file, and leaves no temporary file after a failed write; (e) pending directories: a hidden directory is excluded, edit counts are read, a directory without `plan.json` reads `edits unknown`; (f) `as_dict()["findings"] == api.findings(paths).as_dict()` and the key set of FR-002 present at this phase; (g) FR-007's snapshot equal and no lock file beside the wiki after each run; (h) with `wiki_studio.backends.resolve_backend` and `wiki_studio.api.resolve_backend` patched to raise (as `tests/test_findings.py` 159-171), every run completes.

### US2 — the verb on the CLI contract

- **FR-009 (the verb, D2)**: `nightly` joins `cli.main`'s dispatch table, `cli._VERBS` (so `_inject_legacy_v1_prefix` passes it through), the parser description's verb list (180-184), `tests/test_cli_contract.py`'s `_VERBS` (29-42) and CLAUDE.md's `cli.py` layout line (33); CLAUDE.md also gains one layout line for `src/wiki_studio/nightly.py` (in US1, when the module lands). The subparser takes the common path options (`--root`, `--wiki-dir`, `--proposals-dir`, `--source-root`, `--lock-timeout`, `--search-cache`) and `--report PATH` and `--json`; US3 adds `--backend`, `--max-proposals` and `--by` (FR-013). Its `description` says what the verb runs, that it never promotes or approves and writes nothing in the wiki, and lists its uses of the exit codes as they stand at the end of the phase (US2: 0, 1, 6; US3 adds 2, 3, 4, 10 and the precedence of FR-010). No new exit code; the top-level epilog is unchanged.
- **FR-010 (exit codes and their precedence, D9 with the #104 reviewer's notes; the one place the rule lives)**: Codes and meanings (no new code; 0 and 2..11 keep their meaning, 1 stays fatal lint): **0** a completed run, whatever it found or drafted; **1** structural lint failed (report written, nothing drafted, FR-004), or a pre-run refusal: a `--report` path inside the wiki (FR-005), a negative `--max-proposals` or a proposals directory inside the wiki with drafting on (FR-013); **2** the `--backend` name is unknown or its CLI is not on PATH, before lint runs (FR-013); **3** a draft's backend call failed; **4** a draft's response was invalid, out of bounds, or refused by `api.propose`'s validation, or governed schema drift skipped drafting (FR-020, FR-021); **6** the report could not be written, or a proposal write failed (FR-021); **10** the wiki lock timed out while writing a proposal. Pre-run refusals (1, 2) end the run before anything else, so they never combine. When several outcomes occur in one run the code is decided once, at the end, in this order: (1) **the report could not be written: 6, whatever else failed** (a lock timeout or a lint failure included), with the reason on stderr (reviewer note 1); (2) else a lock timeout: 10; (3) else a failed proposal write: 6; (4) else a structural lint failure: 1 (it stops before drafting, so it never combines with 2 and 3); (5) else the first draft failure in processing order, 3 or 4, governed drift counting as a draft failure; (6) else 0. Every non-zero exit prints one `error:` line on stderr naming the cause. README (FR-032) and the verb's `--help` (FR-009) state this rule by reference to its outcomes; no other FR restates the precedence.
- **FR-011 (the no-promote guarantee in code, D20)**: A test parses `src/wiki_studio/nightly.py` with `ast` and asserts it imports nothing from `wiki_studio.promoter` (any import form) and references no attribute or imported name `promote` or `approve`. A second test patches `wiki_studio.api.promote`, `wiki_studio.api.approve`, `wiki_studio.api._promote`, `wiki_studio.api._approve` and every public function defined in `wiki_studio.promoter` to raise, and asserts a run through `cli.main` completes with its expected code: model-free in US2; US3 adds a drafting run with the test backend.
- **FR-012 (US2 tests)**: In `tests/test_nightly_cli.py`, through `tests.conftest.run_cli` (in-process `cli.main`): a clean wiki exits 0 with the markdown on stdout; `--json` prints one JSON object with FR-002's keys present at this phase and exit 0; `--report PATH` writes the file and prints no markdown; a broken wiki exits 1 and the report file holds the violations; a report path inside the wiki exits 1 before anything runs (no file, stderr names the path); a report path whose parent is a regular file exits 6 with `could not write the report` on stderr; that unwritable path on a broken wiki exits 6 (FR-010 (1)); `nightly --help` names `--report` and `--json`; the top-level `--help` names `nightly`; `_inject_legacy_v1_prefix(["nightly"])` and `(["--wiki-dir", "w", "nightly"])` return their input unchanged. `tests/test_cli_contract.py`'s help loops cover the verb through its `_VERBS`.

### US3 — drafting with an explicit backend

- **FR-013 (turning drafting on, D7, D12)**: `api.nightly` gains `backend: str | Backend | None = None`, `max_proposals: int = DEFAULT_MAX_PROPOSALS` (a named constant, 5, in `nightly.py`) and `by: str | None = None`; the CLI gains `--backend NAME`, `--max-proposals N` (`type=int`, default the constant; its help says it counts proposals created and that backend calls are bounded at twice `N`, FR-016) and `--by NAME` (help in `_BY_HELP`'s form, recording plan.json's proposer). Drafting is on only when a backend is given and `max_proposals > 0`. A given backend is resolved by `api.prepare_backend` before lint runs, whatever `max_proposals` is, so a wrong name exits 2 with nothing run; `prepare_backend` is never called with None, so `WIKI_STUDIO_BACKEND`, the deprecated `WIKI_INGEST_BACKEND` and PATH auto-detect are never consulted (the `--backend` help says so, as `lint --backend` does at 404-410, and does not use `_BACKEND_HELP_SUFFIX`). A negative `max_proposals` raises `ValueError` before anything runs (exit 1). With drafting on, a proposals directory that resolves inside the wiki directory (`Path.resolve()`, symlinks resolved) or is the wiki directory raises `ValueError` before lint and before any backend call (exit 1), because `api.propose` would then write in the wiki (owner, 2026-11-17: refused with exit 1 before any backend call; plan departure 9). Without a backend, or with `--max-proposals 0`, `drafting.state` is `off` with reason `no --backend` or `--max-proposals 0`, no backend call is made, and nothing but the report is written (D4).
- **FR-014 (what is drafted and what the prompt shows, D5; cut 2 removes (b))**: Draftable findings are exactly: (a) a `missing-cross-link` finding: its `pages[0]` is the canonical page (`health_lint.py` 305 builds `[canonical] + unlinked`, and `findings` keeps the order) and the description contains `canonical page <pages[0]>` (otherwise the finding is report-only); the editable pages are all of `pages[1:]`, every unlinked page the finding names, however many (owner, 2026-11-17: all unlinked pages, not the first five the description names at 311; no page cap and no flag; the owner confirmed the draft must update every one of them, and a draft that leaves one out is refused by FR-019); the prompt shows the canonical page and every editable page, and the draft must update each editable page (FR-019); (b) a `weak-orphan` finding whose one page is not among the root `index.md`'s intra-wiki links (`health_lint._intra_wiki_links_from(wiki_dir / "index.md", wiki_dir)`; the inbound link of a weak orphan is unique, so absence from the index means it comes from a content page); the prompt shows that page and the root `index.md`. Every other finding is report-only: the review kinds, the conflict kinds, `stale-claim`, `avoid-format`, a weak orphan linked from `index.md`, `superseded-still-indexed` and `no-page-id` (D4, D5). Each shown page is read exactly once with `api.read_page`; its `text` is what the prompt shows and its `sha256` is the `base_sha256` of any `update` of it (FR-018). - **FR-015 (the proposal name, D6)**: A draftable finding's proposal name is `nightly-<kind>-<key>`, where `<key>` is the first 12 hex digits of `sha256(("<kind>\n" + "\n".join(sorted(pages))).encode("utf-8"))` over the finding's `kind` and all its `pages`. The prefix `nightly-` and the length 12 are named constants in `nightly.py` (`NIGHTLY_PROPOSAL_PREFIX`, `NIGHTLY_KEY_LENGTH`), and `nightly.proposal_name(kind, pages)` is the one function that builds it; every name passes `api.check_proposal_name`. - **FR-016 (order, overlap, the proposal cap and the attempt bound; D7 as changed by the owner on 2026-11-17; the one place the caps live)**: Two bounds per run, both counted from zero at the start of each run (no state is kept between runs): the **proposal cap** `N = max_proposals` (`--max-proposals`, default 5) counts proposal directories this run actually created through `api.propose`; the **attempt bound** `2 × N` counts backend calls (draft attempts). The attempt bound is derived from `N` by a named constant `ATTEMPTS_PER_PROPOSAL = 2` in `nightly.py`; it is not a flag and has no environment variable. `N = 0` turns drafting off and makes no attempt (FR-013). Draftable findings are taken in the order `findings` lists them (deterministic for a given wiki). For each, in this order: (1) the name (FR-015); (2) a pending directory of that name means "already proposed" (FR-025); (3) if an editable page of this finding is the target of an `update` in a proposal created earlier in this run, the finding goes under `not_drafted` with reason `overlaps an earlier draft` (two updates from one base would make the second stale at promote); (4) if `N` proposals have been created in this run, it goes under `not_drafted` with reason `cap: proposals`; (5) else if `2 × N` attempts have been made, it goes under `not_drafted` with reason `cap: attempts`; (6) otherwise it is drafted with one backend call, whatever the number of its pages, which uses one attempt; it uses a proposal slot only if `api.propose` creates its directory. So a refused or failed draft (FR-019, FR-021), and a race lost to another run (FR-026), uses an attempt but no slot, and findings later in the order are still drafted while attempts remain; a finding that fails every night is listed under `### Failed` with its reason every night (FR-022) and costs one attempt per run. Steps (2) to (5) make no backend call. A run therefore creates at most `N` proposals and makes at most `2 × N` backend calls.

- **FR-019 (the bounds and the link-only check, D5; owner-confirmed: link existing words only)**: Syntactic, no semantic diff. Definitions in `nightly.py`: an inline link is a match of `(?<!!)\[([^\[\]\n]*)\]\(([^()\s]+)\)` (group 1 the text, group 2 the target); a target resolves from page `P` to `posixpath.normpath(posixpath.join(posixpath.dirname(P), t))` where `t` is the target with any `#fragment` removed, and resolves to nothing when `t` is empty, starts with `/` or contains `:` (a URL or `mailto:`); stripping links to page `C` from a text replaces each inline link whose target resolves to `C` by its text. A **code region** of a page text is (i) every line of a fenced code block, from its opening fence to its closing fence, found with `prose_lint.open_fence` and `closes_fence` (`prose_lint.py` 76-105; the CommonMark fence rule the prose scanner already uses: a run of three or more backticks or tildes after at most three spaces, closed by a run of the same character at least as long; an unclosed fence runs to the end of the text), and (ii) on every other line, every inline code span: from a run of `n` backticks to the next run of exactly `n` backticks on the same line, an unclosed run making the rest of that line code (fail closed). The check reads code regions from the page text it judges (the draft), not from the rendered page. **Which words may become a link**: only words already on the page, since stripping must give back the original byte for byte; so any mention `missing-cross-link` counts may be linked as it stands: the canonical slug, the slug with hyphens as spaces, in any case, or a glossary avoid term of the canonical page (`health_lint.py` 256 counts it as a mention). Linking an avoid term is allowed, and the page keeps the term the glossary says to avoid: the draft cannot replace it with the preferred term, because that changes words; that change is a curator's own edit. A draft is **out of bounds** when any of these holds: it has a `create`; it has an action the finding's kind does not allow; it edits a path not allowed below; it lacks a required edit; or a rule below fails. **(a) `missing-cross-link`**: required and allowed: exactly one `update` for each editable page of FR-014 (all the finding's unlinked pages), no other `update`, and exactly one `append-log` on `log.md`; the rule below is applied to each `update` independently, and every `update` must pass, or the whole draft is refused and nothing is proposed (no partial proposal); for each `update` of page `P`, with original `O` the `read_page` result of FR-014 for `P` (whose `sha256` becomes the edit's `base_sha256`, FR-018) and draft `D` its `new_content`: the UTF-8 bytes of `D` with its links to the canonical page stripped must equal the UTF-8 bytes of `O.text` with its links to the canonical page stripped, byte for byte, and `D` must hold more inline links resolving to the canonical page than `O` does; and no inline link resolving to the canonical page may start inside a code region of `D` (reason `link inside code`), because a link inside a fenced block or an inline code span breaks the code or renders as literal text. Consequence, stated plainly: because every unlinked page must be updated (FR-014), a page whose only mentions lie inside code cannot be linked within bounds, so every draft for that finding is refused whole (the reason recorded is the rule the draft broke: `link inside code`, `adds no link` or `lacks a required edit`), the finding is listed under `### Failed` on every run until a curator changes the page, and each such run uses one attempt of FR-016 and no proposal slot. **(b) `weak-orphan`**: allowed: exactly one `append-index` on the root `index.md` and exactly one `append-log` on `log.md`; the index line holds exactly one inline link, its target resolves from `index.md` to the orphan page, and with that link removed the line contains none of `](`, `][`, `<http`, `://`. **Both**: each append line is one line (no newline except one optional trailing newline); the `append-log` line contains none of `](`, `][`, `<http`, `://`. So a reworded sentence, a new "See also" line, a changed frontmatter line and a second link in the index line are refused (FR-023's fixtures). A refusal is a failed draft with reason `out of bounds: <path>: <rule>` and exit 4 (FR-021); nothing is written. The check runs before FR-018's validators.
